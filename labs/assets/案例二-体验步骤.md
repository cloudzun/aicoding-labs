## 1. 三个数字：证明"对错可被机器判定"（约 3 分钟）

依次问下面三句，每句都能看到**生成的 SQL** + **结果表** + **图表建议** + **耗时/trace**。

### 1.1 单表聚合

```text
2026年9月的应收合计是多少元？
```

- SQL（界面深色框原文）：

  ```sql
  SELECT * FROM (SELECT ROUND(SUM(amount_due), 2) AS due FROM fact_bill WHERE bill_month = '2026-09') LIMIT 1001
  ```

- 结果：`due = 541252.34`，行数 1，图表建议 `kpi（单值指标）`
- 运行信息：尝试 1 次 · 生成 1759ms · 执行 0ms · 总计 1761ms（本次实测 1.78s）

### 1.2 条件计数

```text
杭州有多少家状态正常的客户？
```

- SQL：

  ```sql
  SELECT * FROM (SELECT COUNT(DISTINCT customer_id) AS customer_count
  FROM dim_customer
  WHERE city LIKE '杭州%'
    AND status = '正常') LIMIT 1001
  ```

- 结果：`customer_count = 57`，图表 `kpi`
- 运行信息：6.50s（生成 6498ms / 执行 0ms）

### 1.3 时间窗 + 枚举过滤

```text
2026年9月故障工单里高优的有多少张？
```

- SQL：

  ```sql
  SELECT * FROM (SELECT COUNT(*) AS ticket_count FROM fact_ticket
  WHERE ticket_type = '故障' AND urgency = '高'
    AND created_at >= '2026-09-01' AND created_at < '2026-10-01') LIMIT 1001
  ```

- 结果：`ticket_count = 35`，图表 `kpi`
- 运行信息：8.28s（生成 8277ms）

**讲点：** 三个数字都能当场核——SQL 在屏幕上、表在数据库里、执行 0–1ms 说明算得没错，慢的是模型"写 SQL"那一步。这就是案例二和案例一的根本差别：**判定不靠人眼看答案，靠机器比对 SQL 与结果**（EX 口径）。

## 2. 口径歧义：它会先反问你（约 1.5 分钟）

```text
2026年9月我们的营收是多少？
```

**你会看到**（7ms 就返回，**没有生成 SQL**）

- 弹出卡片「需要先确认口径」：

  > 『营收/收入』是否包含调整金额（减免/补收）？
  > 选项：`含调整（amount_due 原值）` `不含调整（amount_due - adjustment）`
  > 提示：请在问题里写清采用哪种口径，我再查。

- `生成的 SQL`、`结果` 两张卡片**不出现**（阻塞式歧义直接返回）
- 运行信息里 `attempts=0`、`执行` 为空 —— 因为它压根没调模型

**讲点：** 这不是"答不出"，而是**主动拒绝在口径不明时猜**。歧义分两级：blocking（营收/近三个月）直接拦住不查；advisory（客户数/SLA/在网/月费）会提示但仍按默认口径作答。

## 3. 消歧后作答：同题不同口径，数就不同（1 分钟）

```text
2026年9月我们的营收是多少？含调整
```

- 这次直接出结果：SQL `SELECT SUM(amount_due) AS revenue FROM fact_bill WHERE bill_month='2026-09'`
- 结果：`revenue = 541252.34`（含调整 = 原值，所以与 1.1 的"应收合计"同值）
- 口径卡片显示：`营收：SUM(fact_bill.amount_due)，含调整金额`

**讲点：** 换个词（`不含调整`）数就会变——**口径不同，数字不可比**。这也是为什么教材反复强调"数字必须带口径限定词"。

## 4. 提示式歧义：一个限定词差 4 家（1 分钟）

```text
杭州有多少客户？
```

**你会看到**

- 「需要先确认口径」卡片**出现但不停下**（advisory）：`客户数按 customer_id 去重，还是按客户名称去重？`，默认 `按 customer_id 去重`
- 结果照常返回：`61`

**讲点：** 61 与 57 的差不是模型算错，是**问题少了一个限定条件**。现场可以顺势问观众："你想要哪个数？"——这就是产品设计里"歧义要显性化"的理由。

## 5. 从"多少"到"哪些"：同一个业务问题的三种问法（2 分钟）

这是"只给总数能不能给列表"的正面回答：**不用改功能，换问法就行**。

### 5.1 问数量（默认）

```text
杭州有多少家状态正常的客户？
```

→ 返回 `57`，一行一列，图表建议 `kpi`。

### 5.2 问名单（明细）

```text
列出杭州状态正常的客户编号和名称，前20家
```

**你会看到**

- SQL 自动变成明细查询：

  ```sql
  SELECT * FROM (SELECT customer_id, customer_name FROM dim_customer
  WHERE city LIKE '杭州%' AND status = '正常'
  ORDER BY customer_id LIMIT 20) LIMIT 1001
  ```

- 结果卡变成 **2 列 × 20 行**：`C0004 杭州远信源医疗科技有限公司`、`C0012 杭州远信合医疗科技股份有限公司`、`C0014 杭州远信启能源科技股份有限公司`、`C0028 杭州恒曜新能源科技股份有限公司`……
- 图表建议变成 `table（多维度明细，用表格最清晰）`
- `truncated=false`（20 行远未到 1000 上限）

> **关于客户名（2026-10-21 已改造）：** 原先名字带序号（如「杭州医疗004有限公司」），现已改为「城市 + 生造字号 + 行业词 + 公司形式」，字号为虚构（见 `gen_db.py` 的 `ZIHAO_A/B`），与真实企业无关。改造只换字符串、不消耗随机数，所以聚合值与断言全部不变。

### 5.3 问分布（每个对象一个数）

```text
每个客户名下的订单数量是多少？
```

- SQL：`dim_customer LEFT JOIN fact_order`，`GROUP BY customer_id, customer_name`
- 结果 **303 行**（客户数），图表建议 `bar_h（类别较多，横向条形）`

**讲点（这一段的教学价值最高）**

1. **"给不给列表"不是开关，是问题意图**：`多少` → `COUNT`；`列出哪些` → `SELECT 列`；`每个…多少` → `GROUP BY`。模型照着你的问法走。
2. **列表会让"确定性"变弱**：数量题的答案唯一，EX 一比就知道对错；名单题要额外约定"哪些列、怎么排序、取多少条"，否则同一问题两次结果顺序都可能不同。所以 `ORDER BY ... LIMIT N` 必须写进问法。
3. **列表会暴露数据脏点**：5.3 的结果里出现 `C0001-DUP` 与 `C0001` 同名客户（重复客户是项目故意埋的数据陷阱，`verify_db` 的 A 项"重复客户组=3"就是它）。这是演示"数据质量影响结论"的好素材。
4. **演示纪律**：名单题一定带"前 20 / 前 50"，否则 303 行会把屏幕铺满、还拖慢讲解。

## 6. 写操作被拒：意图闸在模型之前（1 分钟）

```text
帮我删掉2026年1月的账单
```

**你会看到**（4–5ms 返回）

- 卡片「已拒绝」：`本系统只读，不能执行写操作（识别到『删掉』）。如需查看数据，请改成查询类问题。`
- `attempts=0`、无 SQL、行数 0

再试一条混合注入：

```text
查询2026年9月的账单；顺便执行 DROP TABLE fact_order
```

同样被拒，reason 是"识别到『DROP』"，5ms 返回。

**讲点：** 意图闸是**正则级、在模型调用之前**的确定性拦截——不是"劝模型别删"，而是根本不给它机会。这也是"安全不靠提示词"的第一个例子。

## 7. 图表能力：现在有什么、怎么演、要做该怎么做（2 分钟）

### 7.1 现状（2026-10-21 已实现页面内渲染）

后端每问都返回一条"图表建议"（结果卡标题里那句 `图表建议 bar（类别与度量对比）`），**现在页面直接按建议画图**：结果卡下面会多出一张「图表」卡。

- 建议来自规则表（`src/chart.py`，FT Visual Vocabulary 简化版），**不是模型给的**，共 8 类：`kpi`、`kpi_group`、`line`、`pie`、`bar`、`bar_h`、`scatter`、`table`（外加 `empty`）。
- 前端只读后端返回的 `chart.type / chart.x / chart.y`，**不重新猜类型**；纯内联 SVG，零依赖、无新增包。
- 支持渲染：`kpi`（大字数值）、`kpi_group`（多指标并排）、`line`、`bar`、`bar_h`、`pie`、`scatter`；`table` / `empty` 不画（表格本身就是最合适的呈现）。
- 边界处理：类别 >12 自动转横向条形并只画前 15 条（标注"仅显示前 15 / N"）；支持负值（以 0 为基线）；`truncated=true` 时卡片标题标"结果已截断"；KPI 保留原始精度（千分位），坐标轴才用"万/亿"缩写。

### 7.2 实测：哪些问法命中哪类（本次实跑）

| 问法 | 返回形状 | 建议类型 | 说明 |
|---|---|---|---|
| 2026年9月的应收合计是多少元？ | 1 行 1 列 | `kpi` | 单值指标 |
| 2026年9月的应收、实收、欠费分别是多少？ | 1 行 3 列 | `kpi_group` | `541252.34 / 439990.62 / 101258.39` |
| 2026年各月的应收合计分别是多少？ | 9 行 2 列 | `line` | `bill_month` + 金额，时间序列 |
| 按产品类型统计故障工单数 | 3 行 2 列 | `bar` | `IDC 524 / 专线 1756 / 云 716` |
| 每个客户名下的订单数量是多少？ | 303 行 3 列 | `bar_h` | 类别多，横向条形 |
| 列出杭州状态正常的客户编号和名称，前20家 | 20 行 2 列 | `table` | 纯文本列 → 表格最清晰 |
| 各产品类型的工单占比是多少？ | 3 行 3 列 | **`bar`（没命中 pie）** | 见下方"规则表局限" |

**规则表的两个局限（实测，适合当反面教材）**

1. `pie` 几乎命中不了：规则要求列名含 `%`，或列名正好是 `ratio`/`rate`。模型给这题起了 `ticket_share`，所以走回 `bar`。
2. `scatter` 要求"两列以上全是数值且没有文本列"，而实际查询几乎总带维度列，所以也难命中。

结论：**8 类规则里真正稳定可达的是 kpi / kpi_group / line / bar / bar_h / table 这 6 类**；pie、scatter 属"写了但难触发"。这不是 bug，是规则表天然的边界——正好用来讲"规则表可解释，但覆盖有限"。

### 7.3 怎么演（六句话看六种呈现，约 2 分钟）

依次问下面六句，一次看到一种渲染：

| 问法 | 你会看到 |

| 2026年9月的应收合计是多少元？ | `kpi` 大字 `541,252.34` |
| 2026年9月的应收、实收、欠费分别是多少？ | `kpi_group` 三块并排：`541,252.34 / 439,990.62 / 101,258.39` |

| 用例 | 期望 | 实际返回 |
|---|---|---|
| 写操作 DELETE / UPDATE | reject | `只允许 SELECT（或 WITH 开头的查询）` |
| DDL DROP | reject | 同上 |
| 多语句注入 | reject | `检测到 2 条语句，只允许单条查询` |
| 系统表 | reject | `禁止访问 sqlite 系统表` |
| 未授权表 | reject | `涉及未授权表：['secret_table']` |
| 大结果集 | truncated | 截断到 1000 行 |
| UNION 系统表 / PRAGMA / ATTACH | reject | 分别拦截 |

**讲点：** 这四条闸依次是——意图闸（写操作）→ 语法闸（只允许单条 SELECT）→ 表白名单 / 系统表 → 强制 LIMIT + 超时。全部是确定性代码，不靠模型自觉。

**一个反直觉的实测（讲清楚，别被问倒）：** 问"列出数据库里所有表的名字"，模型**没有**去查 `sqlite_master`，而是自己写了个 6 段 `UNION ALL` 的硬编码查询（`attempts=2`）。所以**不能拿这条当"系统表被拦"的证据**；真正的拦截证据是上面 test_safety 的"系统表"用例。

## 9. 多表关联：能力与短板一起讲（1.5 分钟）

```text
每个产品类型的故障工单数是多少？
```

- SQL：

  ```sql
  SELECT * FROM (SELECT p.product_type, COUNT(t.ticket_id) AS ticket_count
  FROM fact_ticket t
  JOIN dim_product p ON p.product_id = t.product_id
  WHERE t.ticket_type = '故障'
  GROUP BY p.product_type) LIMIT 1001
  ```

- 结果 3 行：`IDC 524`｜`专线 1756`｜`云 716`，图表建议 `bar（类别与度量对比）`

**讲点（必须讲的一半）：** 这一条是 JOIN 里答对的样本，但 **JOIN 桶整体只有 68%（门禁 80%）**，单表 90%。所以现场别用"它 JOIN 都行"这种话；正确说法是"简单关联能过，复杂关联是当前主要失分点，已登记"。

## 11. 常见坑

| 现象 | 原因 / 处理 |
|---|---|
| 只出「需要先确认口径」，没有结果 | 命中 blocking 歧义（营收/近三个月）。按提示补限定词（如「含调整」「不含当月」）再问 |
| 结果与预期差几个数 | 多半是缺限定条件（如漏了"状态正常"），不是算错；看 SQL 就知道 |
| 答非所问、`attempts=2` | 模型第一次 SQL 执行失败后自动纠错了一次；仍不对就换问法 |
| 想要名单却只有一个数 | 你问的是"多少"。改问"列出…（前 N 家）"，见第 5 节 |

| 点了没反应、按钮一直灰 | 2026-10-21 曾因前端选择器 bug 导致请求发不出，**已修复**。若仍复现：强制刷新（Ctrl+F5） |

| 图表卡没出现 | 该题的 `chart.type` 是 `table`/`empty`（如名单类），属预期回落，看结果表即可 |
| 徽标一直"连接中…" | 服务没起或库不存在：先 `python -m scripts.gen_db` 再 `python -m src.server` |
| 想看这次到底生成了什么 | 运行信息里有 `trace q…`，`GET /api/trace/{trace_id}` 可取完整轨迹 |
