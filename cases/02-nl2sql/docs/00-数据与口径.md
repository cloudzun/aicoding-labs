# 环 0 · 数据与口径（NL2SQL 项目）

> **本环的存在理由：** NL2SQL 的"答对"是可执行判定的（`EX`），但如果**口径、分母、比对规则**不先定死，EX 数字同样不可信。
> **本环门禁：** 库结构、埋点、EX 规则、题型分桶、语义层定义——五项有书面结论才进环 1。
> **状态：** 已关闭。库已生成并通过 11 项完整性断言（`evidence/db-verify.json`）。

---

## 1. 目标与非目标

### 1.1 目标

1. **可自动判定**：EX（执行结果一致率）全自动，**零 judge 依赖**——这是与 RAG 项目最大的不同，也是本项目能绕开"judge 不稳定"的原因。
2. **可约束**：只读、表/列白名单、强制 LIMIT、超时四道**确定性安全闸**，不靠提示词。
3. **可解释**：界面上 SQL 可见，结果可核对（行数、时间范围、用到的口径）。
4. **可复现**：库由固定 seed 生成，任何人重跑得到同一份数据与同一 sha256。

### 1.2 非目标（明确不做）

- ❌ 多轮追问与指代消解（只演示，不进验收）
- ❌ 写操作（INSERT/UPDATE/DELETE/DDL 一律拒绝）
- ❌ 跨库/跨数据源联邦查询
- ❌ 模型微调
- ❌ 完全离线（生成走 magpie，上游仍是云端）

## 2. 数据来源与合规

| 项 | 结论 |
|---|---|
| 来源 | **自建合成库**，`scripts/gen_db.py` 确定性生成（seed=20261020） |
| 真实性 | **完全虚构**，客户名/产品/工单均为程序生成，不含任何真实企业数据；客户名为"城市 + 生造字号 + 行业词 + 公司形式"（如「杭州远信源医疗科技有限公司」），字号为虚构，与真实企业无关 |
| 可复现 | 同一 seed + 同一脚本 → 同一 sha256；当前 `d1f5872ee5811cea…`（2026-10-21 客户名改造后） |
| 许可风险 | 无（无第三方数据） |
| 拒绝方案 | 公开基准（BIRD/Spider/中文集）：许可未核实、schema 与运营商场景不符；客户真实库：涉敏且周期不可控 |

## 3. 库结构（6 表 / 8,584 行）

| 表 | 行数 | 作用 |
|---|---|---|
| `dim_customer` | 303 | 政企客户（含 3 组刻意重复） |
| `dim_product` | 36 | 产品（专线/云/IDC） |
| `dim_employee` | 40 | 客户经理/维护班组/客服 |
| `fact_order` | 2,000 | 订单（月费、折扣、生效/退订） |
| `fact_ticket` | 5,000 | 工单（故障/投诉/开通，响应/解决时间） |
| `fact_bill` | 1,205 | 月度账单（应收/实收/欠费/调整，**挂 order_id**） |

**关键设计：账单挂 `order_id` 而不是 (customer, product)。** 原因：同一客户同一产品可能有多笔订单，只按客户+产品无法对账，会导致"应收是否算对"这类问题永远无法判定（初版就踩了这个坑，见 §7）。

## 5. EX 口径（核心）

### 5.1 指标定义

```
EX（执行结果一致率） = 结果集与标准结果集一致的题数 / 有效判定题数
```

**分母 = 150（主集全部题）；无效判定（SQL 无法执行且标准答案明确）计入"未通过"，不剔除。**

### 5.2 比对规则（先定死，避免验收扯皮）

| 规则 | 取值 | 理由 |
|---|---|---|
| 列数 | 必须一致 | 列数不同说明聚合维度不同 |
| 列顺序 | **无关** | 多解 SQL 列序可不同 |
| 列名 | **无关** | 别名不影响正确性 |
| 行顺序 | **无关**；仅当 SQL 含 `ORDER BY` 时校验前 N 行顺序 | ORDER BY 是题面要求的一部分 |
| 浮点容差 | 0.01 | 计费金额两位小数 |
| 数值类型 | 宽容（`"1"` 与 `1` 视为相同） | 不同 SQL 输出类型可能不同 |
| 空结果 | 空集 = 空集 | 不区分"0 行"与"全 NULL" |
| 多解 SQL | **都接受**，只看结果集 | 这是 EX 相对 EM 的核心优势 |

### 5.3 辅助指标

| 指标 | 定义 | 阈值 |
|---|---|---|
| **可执行率** | 生成的 SQL 能成功执行的比例 | ≥95% |
| **安全违规率** | 触发只读/白名单/LIMIT 闸的请求比例 | 记数，不设阈值（演示用） |
| **纠错成功率** | 首次失败后 ≤2 次重试内成功的比例 | ≥50% |
| **歧义识别率** | 15 条歧义题中"主动反问"的比例 | ≥60%（人工判定） |
| **回收率（latency）** | 首次返回（含 SQL）p95 / 结果完成 p95 | ≤2s / ≤4s |

## 6. 评测集设计

### 6.1 主集 150 题（按 SQL 结构分桶）

| 分桶 | 题数 | 说明 |
|---|---|---|
| 单表筛选 | 40 | WHERE / IN / LIKE / NULL |
| 两表 JOIN | 30 | 订单×客户、工单×客户 |
| 三表 JOIN | 20 | 账单×订单×客户 / 工单×客户×产品 |
| 聚合分组 | 30 | GROUP BY + 排序 + Top N |
| 时间窗口 | 15 | 月/季度/近三月、同比环比 |
| 否定与空值 | 15 | NOT IN、IS NULL、排除退订 |

### 6.2 歧义集 15 题（人工判定，不用于 EX）

考"该反问而不是硬答"：营收含不含调整、近三月含不含当月、"客户数"是否去重、SLA 以标记还是时长、"在网"是否含待生效、金额是月费还是折扣后。

**判定标准**：主动指出歧义 + 给出口径选项 = correct；直接给单一数字 = wrong；给数字但注明假设 = partial。

### 6.3 锚点集 20 题（人工写，与生成流程隔离）

用途：校准自动 EX 与人工判断的一致率（要求 ≥85%）。上一轮的教训是"自动指标会自欺"，这一轮用它做刹车。

## 7. 语义层契约（必须与引擎一起交付）

| 指标/概念 | 定义（写进 prompt 与文档） |
|---|---|
| 营收 | `SUM(fact_bill.amount_due)`（**含调整**） |
| 实收 / 欠费 | `SUM(amount_paid)` / `SUM(arrears)` |
| 折扣后月费 | `fact_order.monthly_fee * fact_order.discount_rate` |
| 在网 | `cancel_date IS NULL AND effective_date <= 统计日` |
| 新增订单 | 按 `order_date` 计，不按 `effective_date` |
| **SLA 超时** | 以**时长口径**为准：`(resolved_at - created_at) > 4 小时`；与 `sla_flag` 矛盾时单独报告矛盾数 |
| 近三个月 | **最近 3 个完整账期（不含当月）** |
| 千兆专线 | `product_type='专线' AND bandwidth_mbps >= 1000` |
| 高优工单 | `urgency='高'` |
| 客户数 | 按 `customer_id` 去重（A 类重复客户会让"按名称计数"偏大） |

> **这些定义同时是三样东西**：prompt 的上下文、gold SQL 的依据、验收时的口径解释。三者不一致就会出现"系统答对了但客户不认"。

## 8. 本轮踩到并修掉的设计缺陷（记录在案）

| 缺陷 | 现象 | 修法 |
|---|---|---|
| 客户名组合式生成 | 出现 83 组同名客户（只要 3 组），"客户数"类问题到处歧义 | 名称唯一化，只保留 3 组刻意重复；2026-10-21 起改为「城市+生造字号+行业词+公司形式」（不再带序号，字号由确定性函数派生） |
| 账单不挂 order_id | 同客户同产品多订单时应收无法对账，"H 应收不符"误报 127 行 | 账单表增加 `order_id`，主键改 `(bill_month, order_id)` |

**教训：库的"看起来像真的"和"能被判定"是两件事。** 前者靠文风，后者靠主键与外键设计。
