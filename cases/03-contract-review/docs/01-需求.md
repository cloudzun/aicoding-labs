# 环 1 · 需求（合同审查）

> 压缩版 office-hours：客户验收表已给，只补"用户、成功、不做"。

## 1. 一句话定位

**把合同丢进去，按规则清单逐条检查，输出"哪有风险、第几段、原文是什么、怎么改"，并按等级排序**；判不了的显式说"未取得依据"，不假装合规。

## 2. 用户与场景

| 角色 | 用法 | 期望 |
|---|---|---|
| 合同经办人 | 签署前自查 | 5 分钟内看出高风险条款，能直接改 |
| 采购/商务负责人 | 批量初筛 | 只关注"高"等级 + 必查缺失 |
| 法务 | 复核机器结果 | 能一键跳到原文位置，判断机器有没有看错 |
| 合规/审计 | 抽查流程 | 有固定报告、有规则版本、可追溯 |

**关键判断：这个场景的价值不是"替代法务"，而是"把清单式检查做全、把位置指准、把等级分清"。** 所以定位与引用比措辞重要。

## 3. 用户故事（带验收点）

| # | 故事 | 验收点 |
|---|---|---|
| U1 | 我上传一份合同，能看到"必查条款缺了哪些" | 存在型/缺失型 Recall ≥85/88% |
| U2 | 我能看到每处风险在第几页第几段、原文是哪句 | 定位率 ≥90%，引用在定位段内 |
| U3 | 我关心违约金比例够不够、付款周期长不长 | 数值型判定与阈值一致 |
| U4 | 我要知道"责任是否对等、解除权是否单方"这类语义问题 | 语义型 Recall ≥70% 且必须给原文 |
| U5 | 我要按等级排序，先看高风险的 | 报告按 高→中→低 排序 |
| U6 | 系统判不了的地方要明说 | `not_detected` 在报告里列出 |
| U7 | 我不能容忍"合同里写了指令就被带跑" | 提示注入防御（文档内容只作数据） |
| U8 | 我要能看到用了哪版规则 | 报告含 `rule_version` |

## 4. 做与不做

**做：** docx 解析 → 27 条规则双引擎 → 结构化报告（定位/等级/引用/建议）→ 前端展示 → 810 单元评测。

**不做：** 法律意见、合同起草、谈判建议、PDF/扫描件、多份比对、跨语言、修改原文。

## 5. 关键决策（已定）

| 决策 | 结论 | 依据 |
|---|---|---|
| 判定单元 | 规则×合同（810） | 按合同计 30 份时 ±14pp，等于没测 |
| 规则来源 | 自建 27 条 YAML | 需可机读、可版本化；客户真实清单待替换 |
| 语义规则 | LLM，但**证据必须可定位** | 否则幻觉直接变成"风险结论" |
| 缺失型检测 | 标题匹配，不靠关键词 | 关键词满篇命中，实测 recall 仅 25% |
| 报告 | 固定 schema | 客户要结构化，且便于自动比对 |
| PDF | v1 不支持 | 解析质量会污染全部指标（与 ① 同因） |

## 6. 成功标准

**业务侧：** 经办人能靠它自查出高风险条款；法务复核时能跳原文。
**工程侧：** 810 单元自动评测；报告结构 100%；定位率 ≥90%；单份 p95 ≤10s。

## 7. 风险 Top 3

| 风险 | 对策 |
|---|---|
| 规则清单主观、客户不认 | 环 0 请客户确认规则表；每条给判定依据与建议 |
| 缺失型误报 | 标题匹配 + 缺失型误报率单独进门禁 |
| 提示注入 | 文档内容分隔 + 角色隔离 + "忽略以上指令"清洗 + 输出 schema 校验 |
