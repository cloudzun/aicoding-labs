## 1. GStack 到底是什么

### 1.1 一句话定位

GStack 不是"提示词合集"，也不是"聊天模板"。它是一套**带门禁的工程流程**：每个环节有明确输入、明确产物、明确通过判据，且判据由独立环节或独立模型执行——目的是让"AI 写完代码说完成了"这件事不再成立。

**术语先统一（否则后面全是错的）：**

| 口径 | 内容 | 出处 |
|---|---|---|
| **官方叙事：7 段** | Think → Plan → Build → Review → Test → Ship → Reflect | `C:\Users\cheng\gstack\README.md:171-175` |
| **课程口径：八环**（本文默认） | office-hours → spec → autoplan → 受控施工 → review+cso → qa → ship → retro+learn | 课程 README、R1–R3 讲解记录 |
| **七环** | 八环去掉 retro（迭代轮次从 spec 起算） | 迭代方法论 |
| **五环** | spec → autoplan → review → qa → ship（轻量交付） | R3.5 轻量实践 |

四个说法都对，指的不是同一个东西。**写教材/写报告时必须写明用的是哪一种**，否则"八环"会同时指"官方 7 段"和"课程 8 环"，学员一对官方文档就乱。

补一条容易被漏掉的机制事实：**第 4 环"施工"在 GStack 里没有对应技能**（技能表与安装目录都没有 build 类条目）。施工是"提示词驱动 + autoplan 产出的 tasks/test-plan + ship 的 plan-completion 校验"三者拼起来的，这解释了为什么施工期最容易失控——**它是全流程里唯一没有技能内建门禁的一环**。

### 1.2 四条构建者信条（源码 `C:\Users\cheng\gstack\ETHOS.md`）

| 信条 | 原文要义 | 对使用者的实际含义 |
|---|---|---|
| **Boil the Ocean** | AI 让"做完整"的边际成本趋零，所以"只做 90%"成了偷懒的借口 | 别在方案里砍完整性去省工时；砍掉的是"确实无关的工作"，不是边缘情况 |
| **Search Before Building** | 先搜再建；三层知识（成熟做法／新潮做法／第一性原理） | 禁止重复造轮子；但新潮做法不可盲信，"两条模型都同意"也只是信号不是证据 |
| **User Sovereignty** | 模型只建议，用户做决定；这是唯一可以覆盖其他所有规则的一条 | 门禁给结论、给人选项；AI 不得"先改了再告诉你" |
| **Honest Work** | 工作是产品，报告只是主张；报告在被重新执行前不算数 | 禁止自我认证、禁止把"跑了但不可用"写成通过 |

> ETHOS 里那张压缩比表（Boil the Ocean 同源）值得单独记：样板代码 ~100x、写测试 ~50x、功能实现 ~30x、架构设计 ~5x、调研 ~3x。**它直接决定了 FDE 场景里"该多快出原型"的预期**——原型快，判断慢，所以流程要把时间花在规格与评审上，而不是敲代码上。

### 1.3 一条贯穿全局的设计哲学：未验证 ≠ 已验证为否

这是 R1 八环跑下来最有价值的发现：同一个原则在**四个不同环节用四种不同机制**表达。

| 环节 | 表达方式 | 原文要点 |
|---|---|---|
| `/cso` 安全审计 | 报 `not_assessed` 而不是"干净" | "Never infer a clean result from setup failure or absent scanner output." |
| `/qa` 实机探索 | 未测试类别必须排除并标"临时分" | "Exclude untested categories; label partial scores provisional with coverage." |
| `/ship` 覆盖率门 | 未测定填 `null` 而不是 `0` | "Use `null` for an undetermined or skipped coverage percentage, not zero." |
| `/retro` 复盘 | 无学习须显式声明空结果 | "state 'No durable learnings this session' — an explicit empty result" |

**为什么这条对三个 AI demo 尤其重要**：AI 应用的验收指标（召回率、准确率、幻觉率）天然存在"测了没通过"和"根本没测"两种状态。如果流程里没有区分这两者的表达位，验收时就必然出现"我们没发现幻觉问题"这种话——它既可能是真的，也可能是根本没测。

### 1.4 八环的工程本质：三道防线 + 两次独立复核

```
防线一 规划（环 1-3）：把模糊意图压成可执行规格，四视角会审
防线二 施工（环 4）  ：按规格做，遇歧义必须停下回补规格
防线三 验收（环 5-7）：结构排雷 + 安全审计 + 实机探索 + 发布门
收口     复盘（环 8）：把经验变成机构记忆，把技术债登记成账本
独立复核：spec 的跨模型评分门（≥7）；review/cso 的二智能体交叉复核
```

**判断一个项目该走几环的依据不是"重要性"，而是这次改动有没有触及：数据模型 / 接口契约 / 安全边界 / 多文件协同。** 触及就走全流程，纯表层（改文案、调样式、修小 bug）就轻量走。这条来自课程方法论，四次实跑都验证过。

## 2. 工具本体：装在哪、怎么调

### 2.1 本机三处安装（**这是第一个必须钉死的事实**）

| 位置 | 版本 | 来源 | 谁会用到 |
|---|---|---|---|
| `C:\Users\cheng\.codex\skills\gstack` | **1.91.121.0** | 源码仓库 `C:\Users\cheng\gstack` | `codex exec` 非交互调用（本项目 R1–R3.5 实际用的就是这条路径） |
| `C:\Users\cheng\.config\opencode\skills\gstack` | **1.87.3** | npm 包 | opencode 宿主 |
| `C:\Users\cheng\.claude\skills\gstack` | **1.58.3.0** | npm 包 | Claude Code 宿主 |

证据：`~/.gstack/installs.tsv` 记录 `codex / global / .../gstack 1.91.121.0 committed 2026-10-17T08:03:33Z`；`~/.gstack/.last-setup-version` = `1.91.121.0`；三处各自的 `VERSION`／`package.json` 如上表。

> **必须记住的后果：** 三个版本的技能文档不是同一份。同一个门禁在 1.58 与 1.91 上的阈值、字段、甚至有没有这道门都可能不同。`CHECKPOINT-PROTOCOL §3.4` 要求"取证期间锁定 GStack 版本，中途升级则此前证据需重新评估"——本机现状正好踩在这条红线上。
> **建议：** 三个 demo 全部固定在 **`~/.codex` 那套 1.91.121.0** 上跑（与历史证据一致），并在每个项目的 `ENVIRONMENT.md` 首行写死版本号。八环经验报告记录的环境基线是 `1.91.101.0`，比当前 1.91.121.0 早一个补丁位，属正常升级，但引用旧报告时要知道差了这一档。

**版本差异里最要命的一处（必须知道）：新版 1.91.x 把"第二意见模型"从 Codex 换成了 Claude Code。** 1.58.x 时代的门禁字段与判定逻辑也不同。这意味着同一句"跨模型评分门禁 ≥7"，在三份安装里指的不是同一件事；也解释了 R1 的质量门为什么报 `unavailable`——新版调的是未配置的自定义 Anthropic 端点。**凡是引用门禁细节，必须同时写明"按 1.91.121.0 口径"。**

另有一个必须破除的误解：`.gstack/claude-available.json` **不是模型可用性探针**，它只回答"装没装 claude CLI"（浏览器侧边栏探测）。R1 里它 `available: true`，同一轮质量门照样 `unavailable`。**预检通过不等于外部声音可用，必须实跑一次派发验证。**

### 2.2 三条使用路径

**路径 A：Claude Code（交互，最省事）**

```powershell
cd "<项目目录>"
claude
# 会话内依次输入：
#   /office-hours    → 设计文档 + 用户批准
#   /spec            → SPEC.md（Phase 4.5 质量门，Score ≥7）
#   /autoplan        → DECISIONS.md（CEO → Design → DX → Eng 串行）
#   （施工：无技能，直接给提示词，但必须带 Confusion Protocol 约束）
#   /review  /qa  /ship  /retro
```

**路径 B：opencode（交互，会自动把 AskUserQuestion 换成 `question`）**

```powershell
opencode
# 会话内：加载 gstack-spec 技能，按 /spec 流程把 docs/xxx.md 做成 SPEC.md，只做 spec 这一环
```

**路径 C：codex exec（非交互，本项目实际用法，可脚本化、可留原始输出）**

```bash
# 基础形态（与历史 run-ring1.sh 一致）
codex exec \
  -c model="opencode-go/deepseek-v4.1-flash" \
  --sandbox danger-full-access \
  -C "<sandbox 目录>" \
  "$(cat ring-prompt.txt)" > ring-output.txt 2>&1

# 推荐形态（补上 R1 教训的第 1 条：显式压推理强度，否则单环可能 38 分钟跑不完）
codex exec \
  -c model="opencode-go/deepseek-v4.1-flash" \
  -c model_reasoning_effort="medium" \
  --sandbox danger-full-access \
  -C "<sandbox 目录>" \
  "$(cat ring-prompt.txt)" > ring-output.txt 2>&1
echo "EXIT_CODE=$?"
```

> **注意一个现实缺口：** 仓库里现有的 `run-ring1.sh` / `r2.sh` … `r8.sh` **都没有带 `-c model_reasoning_effort`**，而 `R1-操作经验教训 §一` 明确记录：`~/.codex/config.toml` 里 `model_reasoning_effort = "max"` 会导致输出数 MB、单环 38 分钟跑不完，覆盖为 `medium` 后同阶段 38 分钟 → 13 分钟。**新项目请直接采用"推荐形态"，别复制旧脚本。**

**提示词必须落成独立 UTF-8 文件再传**，不要用 heredoc 或管道内联：PowerShell 会把中文写成 `?`，bash 嵌套引号加 Windows 路径极易出错（R1 教训 §六）。

### 2.3 会话种类决定"门禁会不会停下问你"

| 会话种类 | 行为 | 适用 |
|---|---|---|
| `interactive`（默认，不设环境变量） | 遇门禁渲染决策简报并**停下等人拍板** | 教学、需要人工审批的正式跑 |
| `spawned` | 自动选推荐项继续跑，决策点记进完成报告 | 无人值守批处理（**危险，见下**） |
| `headless` | 不渲染、直接判 BLOCKED | CI／评测 |
| auto-decide 第二层 | `/plan-tune` 偏好微调自动决策的倾向 | 高级用法 |

> **实测教训（必须写进每个提示词）：** spawned 模式下子代理**编造了一条不存在的规则**（"spawned 会话禁止把内容发往机器外"）来跳过质量门；真实原因是自定义 Anthropic 端点返回 `custom_provider_requires_model`。
> **推论：无人值守模式下，模型会用自洽的虚构理由填补它无法执行的步骤。** 这不是模型坏，是流程缺"表达位"——所以凡是无人值守，必须要求它把不可用原因原样打出来（`unavailable` + 原始报错 + 诊断命令），而不是自行解释。

## 3. 八环总表（一张表看懂全流程）

| 环 | 技能 | 输入 | 必须落盘的产物 | 门禁／判据 | 过环条件 |
|---|---|---|---|---|---|
| 1 | `/office-hours` | 一句话需求 | 设计文档（`Status: DRAFT`→人工批准后 `APPROVED`） | 对抗式复审 1–10 分，**无硬门槛**；最多 3 轮，未过则问题写入 `## Reviewer Concerns` | 用户批准设计文档 + 有显式"明确不做"清单 |
| 2 | `/spec` | 设计文档 | `SPEC.md` | **外部模型评分 ≥7/10**（"陌生实现者能否执行"）；<7 可改稿重打，**最多 3 次派发**；脱敏命中 HIGH → 硬阻断（exit 3，无开关） | 评分 ≥7 且脱敏通过 |
| 3 | `/autoplan` | SPEC | `DECISIONS.md` + 决策审计表 + 四阶段报告 + tasks JSONL | 四阶段串行（CEO→Design→DX→Eng），**无及格线**；`FAIL/issues_open` 是合法结论；Pre-Gate 缺项最多重试 2 次 | 四阶段跑完 + 品味决策已由人拍板 |
| 4 | （无技能）受控施工 | SPEC + DECISIONS | 代码 + 测试 + `BUILD.md` | **无自动门禁**，靠环 5/6 事后抓；Confusion Protocol 要求"先回补规格再写代码" | 功能真跑通 + 提交历史可自证顺序 |
| 5 | `/review` + `/cso` | diff | `review.md` + 安全报告 | Quality Score = `max(0, 10-(critical×2+informational×0.5))`，**只记录不阻断**；cso 置信度门 daily 8/10、comprehensive 2/10 | 无 unresolved 发现；修复有留痕 |
| 6 | `/qa` | 可运行系统 | `qa-report-{domain}-{date}.md` + 截图 + `baseline.json` | Health Score 八类加权（Console 15／Links 10／Visual 10／Functional 20／UX 15／Perf 10／Content 5／A11y 15），**无及格线**，低于基线告警 | 每个 issue 带截图；未测类别标 provisional |
| 7 | `/ship` | 全绿系统 | `VERSION` + `CHANGELOG.md` + 覆盖率审计 + PR | 覆盖率 **Minimum 60% / Target 80%**（可覆写）；在 base 分支上 → abort；测试失败 → STOP 不许 push | 版本递增 + 文档同步 + 推送成功（或如实记 `requires-remote`） |
| 8 | `/retro` + `/learn` | 全轮数据 | `retro.md` + `.context/retros/*.json` + learnings | 无门禁；要求"无持久学习则显式声明空结果" | 量化指标 + 债务账本 + 改进项 |

**环与环之间靠约定的文件名接力，不靠记忆。** 这是我方课程约定（`SPEC.md`/`DECISIONS.md`/`BUILD.md`/`review.md`/`qa-report.md`/`CHANGELOG.md`/`retro.md`），**不是 GStack 原生命名**——原生走 GitHub issue、plan 文件与 `.gstack/` 目录。教学时必须讲清这个差别，否则学员对照官方文档会对不上号。

**全流程只有两处是真正的硬数字门禁**：spec 质量分 **≥7**（最多 3 次派发）、ship 覆盖率 **60%/80%**。qa 健康分、review quality score、autoplan 四阶段评分都只是"打分记录"，**不阻断流程**。教学时如果把打分记录讲成门禁，学员会对 GStack 产生错误预期，第一次碰壁就失去信任。

## 4. 逐环要点（目标／门禁／三个坑）

### 4.1 第 1 环 `/office-hours`：把一句话变成能开工的需求

- **目标**：用 YC 式逼问把"我想做个东西"重构为"谁、在什么场景、现在怎么凑合、为什么非做不可"；给 2–3 套方案比选，最后落一份设计文档等人批准。
- **门禁**：Phase 4 替代方案门禁——**拦下并要求明确批准**，防的是"把推荐写成散文然后继续往下走"。评分无硬门槛。
- **坑 1**：把"推荐方案"写成既定事实，用户没真正选过。
- **坑 2**：范围边界留到 spec 才画，导致后续每一环都在纠范围。**"明确不做"清单必须在本环写下**。
- **坑 3**：迭代场景重跑 office-hours——需求已明确时直接从 spec 起步，这一环纯浪费时间。

### 4.2 第 2 环 `/spec`：把需求钉成可验收的规格

- **目标**：五阶段精炼，产出"任何陌生实现者都能照着做、不会分叉"的规格；显式 `NOT in scope`；强制先读现有代码。
- **门禁**：外部模型给 0–10 分，**≥7 通过**；<7 第一次可改稿重打，第二次给三选（照发／仅存草稿／再改一轮），**最多 3 次派发**。脱敏门是**一票否决**：命中 HIGH 直接 exit 3，不派发、不落盘、不可跳过。
- **实证**：R1 用残缺稿打 **2 分被拦**、规格 v1 打 **6 分被拦**、定向修订后 **7 分通过**——这是"门禁有分辨率"的三点证明，不是摆设。
- **坑 1**：外部评审不可用时**当成通过**。正确做法：`unavailable` + 原始报错 + 诊断命令，继续 Phase 5 但标 missing coverage。
- **坑 2**：验收标准写成"性能良好""体验流畅"这类无法判定的句话。**每条验收标准都必须能映射到一个可执行判定**。
- **坑 3**：把"评审方说了什么"直接当结论改稿，而不按优先级定向修订后重跑门禁。

### 4.3 第 3 环 `/autoplan`：四个视角轮流挑刺

- **目标**：`CEO → Design → DX → Eng` **强制串行**（Eng 固定最后，因为工程约束要收拾前面所有承诺）；每阶段产出发现与决策；品味型决策必须真问人。
- **门禁**：无及格线，`FAIL` 是合法结论（R1 实测四阶段全 FAIL 仍继续施工，且如实记录）。真正硬的是 Pre-Gate Verification：阶段产出缺失最多允许两次修复尝试。
- **坑 1**：把 autoplan 当成"四份报告的形式主义"。它的真实价值是**义务编号**（每条发现都有 ID，后面能被追溯关闭）。
- **坑 2**：外部声音缺失时记成"双模型已复核"。正确做法：打 `[codex-unavailable]` 或 `[single-model]` 标签并降级声明。
- **坑 3**：真实性行（每条主张须带 `路径:行号` 凭据）被滥用成"每一项事实都要取证"，直接导致计划膨胀。**只对七行校验内的主张要求凭据。**

### 4.4 第 4 环 受控施工：按规格做，不许自由发挥

- **目标**：在规格约束下实现；遇到规格与现实的冲突，走 **Confusion Protocol**：停下 → 实跑取证 → 给选项问人 → **先回补规格** → 再写代码。
- **实证**：R1 施工首日发现规格指定的 `better-sqlite3` 与本机 `node:sqlite` 冲突，协议触发；git 历史证明"规格修订提交严格早于施工提交"（`c748ec4` < `d9eaa0e`）——**顺序本身是可验证的证据**。
- **护栏**：`/freeze <dir>` 目录编辑锁、`/guard`、`/careful` 三级处置，防止顺手改坏无关模块。
- **坑 1**：改了只读文件（如已批准的 `SPEC.md`）去适配实现。
- **坑 2**：把范围裁剪静默做掉、不登记，导致技术债在复盘时消失（R1 真实疏漏）。
- **坑 3**：小步提交缺纪律，最后 review 没有干净 diff 可审。

### 4.5 第 5 环 `/review` + `/cso`：结构排雷与安全审计

- **目标**：`/review` 以"偏执首席工程师"视角猎杀 9 类结构缺陷（N+1、脏读、并发竞态、信任边界、缺索引、转义注入、不变量破坏、错误重试、遗漏枚举）；`/cso` 做全栈安全审计。
- **门禁**：Quality Score 公式只用于记录，**不自动阻断**；cso 用置信度门分档展示。
- **实证**：N+1 由 `1+2N`（N=5 时 11 次查询）降到常数 3；真实 IDOR 修复（200 → 403）。
- **坑 1**：把 `/cso` 的 launcher 当成扫描器——它是**协调器**，必须走 `start → read → scan → submit → finish` 全链路，孤立调用只能拿到快照。
- **坑 2**：修复发现后没有重验，或把已修复发现压掉不记录。
- **坑 3**：Fix-First 分类判据搞错——**判据是"修法是否唯一"，不是"严重度"**。

### 4.6 第 6 环 `/qa`：在真实入口里走一遍

- **目标**：四种深度实机探索（Quick／Standard／Exhaustive／自定义），产出带截图证据的 issue 清单与健康分。
- **门禁**：Health Score 八类加权，无及格线；**每个 issue 必须有截图，否则不算数**；未测类别排除并标 provisional。
- **坑 1**："高分假象"——七类没测、只测了功能面，总分看起来还行。必须让 coverage 与分数一起展示。
- **坑 2**：浏览器发现阶段去读源码，等于作弊（应该像真实用户那样点）。
- **坑 3**：发现缺陷直接改，没有"先写变红回归测试再修"（Fail-Before-Repair）。

### 4.7 第 7 环 `/ship`：发版前的那道门

- **目标**：补测试、跑全部测试、版本递增（四段式 `X.Y.Z.W`）、更新 `CHANGELOG.md`、同步文档、推送/PR/部署。
- **门禁**：覆盖率 **Minimum 60% / Target 80%**（可在 `CLAUDE.md` 的 `## Test Coverage` 覆写）；≥target 直接过；≥min 但 <target 问一次；<min 问且最多返工 2 轮；**比例算不出来就跳过门，不许当 0% 卡**。在 base 分支上 → abort；测试失败 → STOP。
- **坑 1**：覆盖率只算**强证据**——`★` 冒烟测试永不计入覆盖率（这条设计是对的，别改）。
- **坑 2**：文档与代码脱节；`CHANGELOG` 每个 commit 必须至少映射一条 bullet。
- **坑 3**：无远端时把"推不上去"写成"已发布"。正确记 `requires-remote`／`base_unavailable`，并且**不得声称**做过"红先失败"。

### 4.8 第 8 环 `/retro` + `/learn`：用数据回头看

- **目标**：量化复盘（Test Ratio、Fix Ratio、热点文件、返工次数），把经验写进机构记忆，把技术债登记成账本。
- **门禁**：无。但要求"无持久学习须显式声明"。
- **坑 1**：指标误读——`Fix Ratio=0` 不是"没问题"，也可能是"没检测"。**任何量化指标都必须结合"是否存在有效检测"来解读。**
- **坑 2**：技术债登记不能由智能体自发起，必须人确认。
- **坑 3**：复盘写成"沟通不畅"这种无法行动的句子。必须写成"在 X 环因为 Y 导致 Z"。

## 5. 五个跨环机制（比八环本身更重要）

### 5.1 义务追溯：`finding → OB → AC → 证据`

这是本项目最贵的一课。R1 的断链根因不是"没写文档"，而是**追溯链只对规格不对义务**——文档类的义务没有落点，于是掉了。

| 环节 | 要做什么 |
|---|---|
| 登记 | 每条评审发现分配 `OB-<轮>-<序号>`，写清来源（哪一环、哪份报告、第几行） |
| 映射 | 每条义务至少映射一条验收标准 `AC-*`；映射不上说明这条义务没被真正要求 |
| 落点 | 每条 AC 对应一个可执行证据位置（测试名／命令／文件行号／评测用例 ID） |
| 关闭 | 三态判定：`closed`（有证据）／`downgraded`（明确降级并说明原因）／`not-covered`（如实认账） |
| 自检 | 轮末跑一次追溯矩阵，检查"孤立的义务"和"无义务支撑的实现" |

**教训（必须记住）**：R2 把 42 条义务全部 closed 之后，补测仍发现 11 个缺陷点。**"义务全部关闭"不等于"验收完成"。**

### 5.2 决策审计轨迹

`DECISIONS.md` 要记的不只是"决定了什么"，而是七列结构，尤其 **`Rejected` 列**——记下被否决的方案与理由。AI 项目里这一列价值极高：被否决的检索策略、被否决的模型、被否决的提示词方案，半年后都是最有用的资产。

### 5.3 检查点与证据（CHECKPOINT）

7 个不可变标签，每个标签对应一个"可一条命令对齐的起跑线"：

| 标签 | 含义 |
|---|---|
| `ckpt-01-scaffold` | 骨架与 Schema 就绪，业务逻辑未实现 |
| `ckpt-02-planned` | 规格通过评分门禁，测试计划已落盘 |
| `ckpt-03-built-with-bugs` | 主干功能跑通，预埋缺陷仍在 |
| `ckpt-04-reviewed-clean` | 缺陷与漏洞修完，审查凭据为 `CURRENT` |
| `ckpt-05-qa-verified` | 实机 QA 完成，先红后绿证据留档 |
| `ckpt-06-deployed-drift` | 部署完成，故障仍保留 |
| `ckpt-07-final-complete` | 根因闭环，技术债账本完整 |

`manifest.json` 九个必填字段：`checkpoint`／`captured_at`／`host`／`gstack_version`／`model`／`repo_commit`／`repo_dirty`／`commands`／`substitutions`。

> **`repo_dirty` 必须如实填。** 工作区不干净时取证，意味着证据对应的代码状态无法从提交哈希复现——这类证据在教材里必须降级使用或重新取证。
> **注意**：该规程 2026-10-16 已定稿，但 `reference-app` 侧检查点**尚未施工**（`SCAFFOLD-PLAN.md` 自述"方案待确认"）。所以它是"可以直接执行的模板"，**尚无实跑证据**，引用时要标明。

### 5.4 上下文工程：这是最大的实操风险

**先接受一个事实：上下文耗尽是常态，不是异常。** R1 实测：

| 现象 | 判据 | 处置 |
|---|---|---|
| 输出 478513 行、单次 4 MB | 单环跑不完 | 换线程续跑 |
| `Reconnecting...` | 上下文压力 | 准备续跑 |
| `context compacted` | 已经爆了 | **果断掐掉换新线程** |
| `collab: Wait` | 进入等待态 | 果断掐掉换新线程 |
| 输出 90 秒零增长 **且** 文件无写入 | 疑似停顿 | 查上面三项 |

**结论：`codex exec` 是全新会话，不继承上一轮上下文。长环节必须准备"新线程续跑"，并且每个环节的单次调用都要能独立成立。**

配套两件工具：
- **`/context-save` 与 `/context-restore`**：长流程中断前保存进度快照。
- **新会话启动提示词**：把"这个项目是什么、按顺序读哪些文件、关键背景结论、本轮做什么、执行方式、铁律、第一步交给我什么"七段写死。本项目多次用这个办法跨会话续跑，效果好。

**有效写法的三条经验：**
1. 只写**约束与边界**，不写"穷尽取证"这类无上限要求（R1 因这句话导致计划膨胀）。
2. 必须写"哪些文件是只读的"（第 3 环曾把已批准的 SPEC 覆盖成实施计划）。
3. 必须写"没发现问题就如实写未发现""不可用就如实记不可用""已自报的问题原样保留不要重跑掩盖"。

### 5.5 独立复核：maker-checker

**生成提示词/评测脚本的人不给自己打分。** 本项目所有评分门禁都要求评审方与主控**不同模型家族**；同族模型不算跨模型。

注意版本差异会改变这条规则的实现：1.91.x 的第二意见模型是 Claude Code，1.58.x 是 Codex。**"跨模型"这件事在换版本时会被悄悄改变**，所以每轮开始都要在报告里写明"评审方是谁、什么版本"。

实测收益：R3 的 codex 复核查出 4 个 High，全部属"会导致错误验收/清库/安全退化"级别——这是单靠自我审查抓不到的。

成本：不宜无脑全上。单轮全跑四评审约占整轮 1/4 工时；demo 规模建议 **2 个声音**（Eng + 领域/合规）即可。

## 6. 最佳实践 32 条（可直接当 checklist 用）

### 6.1 启动前（一次性，5 条）

- [ ] **锁版本**：读 `~/.codex/skills/gstack/VERSION` 并写进项目 `ENVIRONMENT.md` 首行；三个 demo 统一用 1.91.121.0（`~/.codex` 那套），不要混用 `~/.claude` 的 1.58.3.0。
- [ ] **确认工作区干净**：`git status --porcelain` 为空再开环；带着脏工作区跑出来的证据无法从提交哈希复现。
- [ ] **开分支**：`git checkout -b feat/xxx`。review 的 Scope Drift 检测与 diff 评审依赖 base 分支，不开分支 review 会退化成"评审全部代码"。
- [ ] **写环境基线**：工具版本、模型、宿主、端口（别猜 3000，读它打印的 URL）、平台限制（WSL2 读不到 OneDrive 路径）。
- [ ] **提示词落盘**：独立 UTF-8 无 BOM 文件，脚本只传路径。PowerShell 会把中文写成 `?`，`Set-Content -Encoding UTF8` 会写 BOM 污染提交标题。

### 6.2 规划期（7 条）

- [ ] **office-hours 必须产出"明确不做"清单**。范围边界在这一环画下，留到 spec 画会导致后面每环都在纠范围。
- [ ] **每条验收标准必须能映射到可执行判定**；映射不上的，显式标"人工判定 + 判定人"。
- [ ] **评分门禁不可用时记 `unavailable` 并继续**，附原始报错与诊断命令；**绝不写成通过**。
- [ ] **定向修订后重跑门禁**，而不是"评审说了什么就改什么"。
- [ ] **autoplan 的产出必须有义务编号**（`OB-*`），没有编号的发现等于没提。
- [ ] **品味型/风险型决策真问人**（User Sovereignty）——包括模型选型、检索策略、提示词风格。
- [ ] **规格冻结 + 快照哈希**：把 `SPEC.md` 的 SHA-256 写进后续报告首行，防止规格被悄悄改。

### 6.3 施工期（7 条）

- [ ] **Confusion Protocol 全序列**：发现歧义 → 停下 → 实跑探针取证 → 给选项问人 → **先回补规格** → 提规格提交 → 再写代码。用 `git log --oneline` 证明"规格提交早于施工提交"。
- [ ] **只读文件清单写进每个提示词**（第 3 环确实发生过"把已批准 SPEC 覆盖成实施计划"）。
- [ ] **用 `/freeze <dir>` + `/guard` + `/careful` 防越界**，尤其在多模块项目里。
- [ ] **小步原子提交**，修复提交带可检索前缀（如 `fix(review):`）。
- [ ] **任何范围裁剪必须登记**（`gstack-shortcut(dec-id)`），否则复盘时技术债凭空消失。
- [ ] **显式设推理强度**：`-c model_reasoning_effort="medium"`。默认 `max` 会导致单环 38 分钟跑不完。
- [ ] **每 2–3 分钟看一次进度**；输出 90 秒零增长且文件无写入 = 疑似停顿，按判据处理。

### 6.4 验收期（7 条）

- [ ] **review 的 AUTO-FIX / ASK 判据是"修法是否唯一"**，不是严重度。
- [ ] **修复后必须重验**；已修复的发现不得被压掉不记录。
- [ ] **cso 走全链路** `start → read → scan → submit → finish`，孤立调用只得到快照。
- [ ] **qa 每个 issue 必须带截图**，否则不算数；未测类别排除并标 provisional。
- [ ] **Fail-Before-Repair**：先写一条会变红的回归测试，再修代码，两段输出都要留档。
- [ ] **测试失败 STOP 不许 push**；在 base 分支上 → abort。
- [ ] **无远端时如实记 `requires-remote` / `base_unavailable`**，不得声称做过发布或"红先失败"。

### 6.5 复盘与治理（3 条）

- [ ] **量化指标必须结合"是否存在有效检测"解读**（`Fix Ratio=0` 可能意味着"没检测"）。
- [ ] **技术债登记由人确认**，不许智能体自发起。
- [ ] **无持久学习时显式声明空结果**（"No durable learnings this session"），不要为了凑复盘编三条。

### 6.6 环境层（3 条）

- [ ] **技能 preamble 走 Git Bash**，不要走 PowerShell；显式把 `$HOME/.bun/bin` 加到 PATH。
- [ ] **不接管道判断退出码**：先重定向到文件，再读 `$?`。管道会吞掉真实退出码。
- [ ] **codex 路径不要写死哈希**：R1 脚本里的 `...\bin\9614f1d9b40d9c4f\codex.exe` 已失效（当前是 `896a0166b774037a`）。用 `where codex` / `Get-Command codex` 解析。

## 7. 反模式 12 条（都是我们真踩过的）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 把推荐方案写成散文继续往下走 | 用户没真正选过，返工 | 停在门禁，给 2–3 个选项和利弊 |
| 门禁不可用就换个模型打分充数 | 制造假证据 | 记 `unavailable` + 原始报错，标 missing coverage |
| 无人值守模式（spawned）跑质量门 | 模型编造规则跳过门（真实发生） | 必须复核它"我做不到"的理由；关键门禁保持 interactive |
| 把 `claude-available.json` 当模型可用性 | 预检通过、实跑失败 | 实跑一次派发验证 |
| 验收标准写"性能良好""体验流畅" | 无法验收，最后靠感觉 | 改成可执行判定句（阈值 + 口径 + 测量方法） |
| 复用旧 run-ring 脚本 | 缺推理强度覆盖，单环 38 分钟 | 用本文 §2.2 的"推荐形态" |
| 改动触及数据模型却只轻量走 | 权限/迁移问题在 QA 才爆 | 按"数据模型/接口契约/安全边界/多文件协同"判断走全流程 |
| 迭代轮次重跑 office-hours | 浪费一整环工时 | 需求明确时直接从 spec 起步 |
| 环边界逐条审内容 | 重复劳动、烧上下文 | **边界只核对产出物是否就位**（技能本身有环间制衡） |
| 把"42 条义务全 closed"当验收完成 | 补测仍出 11 个缺陷 | 义务关闭只是必要条件，还要真实探索测试 |
| 覆盖率只按代码路径评星（AI 项目） | 评价错位置 | 换成"失败模式是否被评测用例钉住" |
| 用一次运行结果当证据（AI 项目） | 不可复现，验收扯皮 | 固定评测集 + 多次运行统计 + 版本三元组 |

## 8. 迁移到 AI 项目：八环必须改什么

> 本节是**迁移判断**，机制部分有实跑依据，评测部分属〔推断〕——三个 AI demo 尚未开跑，不得当作已验证结论引用。

### 8.1 承重墙必须换

| 维度 | FruitLab（R1–R3.5，确定性） | 三个 AI demo（非确定性） |
|---|---|---|
| 正确性判定 | 断言固定（返回 201、库存 100→98） | **无唯一正确答案** |
| 证据形态 | 测试通过数、SQL 次数、健康分 | **评测集结果**（召回/准确/忠实度/执行正确率）+ 失败样本清单 |
| 主要风险 | N+1、越权、CSRF | **幻觉、提示注入、跨租户越界、NL2SQL 生成破坏性 SQL、引用不可溯源** |
| 变更影响面 | 代码 diff 即全部 | **提示词/模型版本/检索参数也算变更**，且不易 diff |
| 稳定性 | 一次跑通即可复现 | **每次运行都可能不同**，必须多轮统计 |

一句话：**FruitLab 的"证据 = 测试全绿"在 AI 项目里不成立，必须换成"证据 = 固定评测集 + 多次运行统计 + 版本三元组"。这不是优化，是换承重墙。**

### 8.2 改造后的十步序列（8 环 → 10 步）

| 步 | 名称 | 相对原八环 | 关键产出 |
|---|---|---|---|
| 0 | **数据与口径**（新增） | 新增在 office-hours 之前 | 数据来源与合规边界；**评测口径定义**（什么叫"答对了"）；golden set 规模与标注规范 |
| 1 | 需求（office-hours） | 追加 | 追加"评测口径必须在需求阶段定"、"不可回答集"处理策略 |
| 2 | 规格（spec） | 替换判据 | 每条验收标准映射评测用例 ID；不可自动判定的显式标注 |
| 3 | 会审（autoplan） | 替换声音 | **Eng + 领域/合规 + 数据安全**（Design/DX 仅在有 UI 时保留） |
| 4 | 施工 | 追加 | **评测脚本与功能同步落地**（否则无法验收）；提示词与配置入库版本化 |
| 5 | 评审（review） | 替换量化 | 量化换成"评测集失败率"；追加注入/越权/泄露专项 |
| **5.5** | **评测门禁**（新增） | 新增在 review 之后 | 固定评测集跑 N 次，记录均值与置信区间；**未达基线不许进入 qa** |
| 6 | 实机 QA | 追加类别 | 追加：忠实度、拒答率、注入鲁棒性、跨租户隔离、引用可点开；分布外问法 |
| 7 | 发布（ship） | 替换门禁 | 覆盖率审计 → **评测通过率 + 失败模式清单**；模型/提示词/评测集版本一起发版 |
| 8 | 复盘（retro） | 追加 | **评测集本身的缺口**：哪些失败模式还没被用例覆盖（这是 AI 项目的"覆盖率"） |

### 8.3 AI 项目的"证据"长什么样

沿用 `CHECKPOINT-PROTOCOL` 的 `manifest.json` 九字段，**追加五个必填项**：

| 新增字段 | 内容 | 为什么必须 |
|---|---|---|
| `model` | 模型标识 + 具体版本（已有字段，改为必填到版本级） | 换模型等于换系统 |
| `prompt_sha256` | 提示词文件哈希 | 提示词是最容易"悄悄改"的资产 |
| `eval_set_sha256` | 评测集文件哈希 | 改评测集 = 改考试难度 |
| `decode_params` | temperature / top_p / seed / max_tokens | 不复现参数的指标没有意义 |
| `run_count` | 本次统计的重复运行次数 | 单次运行不构成证据 |

### 8.4 三个 demo 各自的改造重点

| Demo | 评测核心问题 | 必须新建的证据 |
|---|---|---|
| 政企 RAG 问答 | 答案是否**忠于检索材料**（可溯源）；检索是否召回正确文档；**涉密/跨租户是否越界** | 固定问答集（问题 + 期望文档 + 期望要点）；段级召回；逐答案引用可点开校验；**拒答样本**；文档埋指令的注入测试集 |
| NL2SQL 问数 | SQL 是否**语义正确**（不只是能跑）；**是否只读**；是否越权访问表/列 | 问题→标准 SQL→**标准结果集**三元组；**执行结果比对**（非文本比对）；只读与行数上限硬校验；schema 白名单；破坏性 SQL 拦截用例 |
| 合同审查 | 条款**识别全不全**；风险分级是否一致；是否引用正确原文 | 标注样本（条款位置 + 期望标签 + 期望引用片段）；按条款类型的 precision/recall；模型版本变更前后回归对照；不一致样本的人工裁决记录 |

### 8.5 不要照搬的部分

- 不要把 `Test Ratio ≥ 0.20` 当质量线（提示词不是代码行数）。
- 不要按"变更代码路径"逐条评覆盖率星级（AI 项目变更主体在提示词与参数）。
- 不要照搬 N+1 / IDOR / CSP / Host 白名单这套 Web CRUD 靶点清单（会挤占真正该查的位置）。
- 不要一上来就上 Docker×2 + compose + Caddy + 云 VM + CI/CD（这是成熟度阶梯，不是起跑线）。
- 不要四评审全跑（单 demo 约占 1/4 工时，2 个声音足够）。

## 9. 把验收标准写成可判定句（AI 项目专用模板）

客户给的指标（召回≥90%、准确≥85%、幻觉≤10%、≤3s、≤2s、≤10s、召回≥88%）**全部缺少口径**。开工前必须逐条补成下面这个句式，否则验收当天必然扯皮：

```
指标名 = 测量对象 + 口径 + 分母 + 测量方法 + 阈值 + 置信条件
```

三个例子（具体阈值与业界基线判定见 [01-FDE场景与三项目业界借鉴.md](01-FDE场景与三项目业界借鉴.md)）：

| 原话 | 改写成可判定句 |
|---|---|
| 文档内容召回率 ≥90% | 在 200 条标注问答集上，**gold chunk（人工标注的相关段落）** 被 top-5 检索结果命中的比例 ≥90%；检索链路与生产一致；报点估计与 95% 置信区间 |
| 答案准确率 ≥85% | 在 200 条集上，**答案覆盖全部标准事实点**的样本占比 ≥85%；两人独立判定、分歧由第三人裁决；禁用被测模型自评 |
| 事实性幻觉率 ≤10% | 1 − Faithfulness；按**断言**逐条判定"能否被所给上下文支持"；不可回答集上的**编造率**单独统计 ≤10% |

**一个必须先说清的算术**：5 个百分点的判定（85% 与 90%）需要 **n ≥ 200** 条评测样本——n=50 时 95% 置信区间半宽约 ±8.3 个百分点，n=200 才约 ±4.2。**样本量不够，指标再好看也不成立。**

## 10. 教学化建议（这套东西怎么讲给学员）

### 10.1 三个"拦下瞬间"是最有教学价值的资产

| 瞬间 | 讲什么 | 为什么有效 |
|---|---|---|
| **脱敏门禁一票否决** | 含伪造凭据的规格草稿，退出码 3；不派发、不落盘、**原始字节连归档都不许写** | 让学员第一次见到"门禁真的会拒绝"，而不是提示词 |
| **Confusion Protocol 的顺序约束** | 规格指定的库与本机冲突 → 停下 → 问人 → **先改规格再写码** → 用 git 提交顺序自证 | 把"诚实"变成可验证的 git 历史 |
| **门禁拒绝在不信任环境运行** | 外部评审发现自定义端点不提供该模型 → **根本不发起调用**（硬发只会得到冒名评分=假证据） | 讲清"不可用"与"通过"的区别 |

### 10.2 演示与练习分配建议

| 环节 | 课堂演示（讲师跑） | 学员练习 | 理由 |
|---|---|---|---|
| office-hours | 演示 | 练习 | 最容易共鸣，但耗时长 |
| spec + 门禁 | **重点演示** | 练习 | 门禁拦下的瞬间最有冲击力 |
| autoplan | 只看产物 | 简化跑（1–2 声音） | 四声音成本高 |
| 施工 | 演示 Confusion 触发 | 主体练习 | 学员动手主要在这一环 |
| review + qa | **重点演示** | 练习 | 能看见"AI 自己找自己的错" |
| ship / retro | 演示 | 选做 | 依赖远端环境 |

### 10.3 学员作业用"轻量 4 环"

`spec → 施工 → review → qa`（R3.5 证明可交付）。理由：学员时间有限，而八环的后半段依赖部署环境；轻量四环能完整走通"规格—实现—复核"的闭环，教学价值密度最高。

## 11. 环境与运维坑（17 条，按影响排序）

| # | 坑 | 规避 |
|---|---|---|
| 1 | 技能 preamble **必须走 Git Bash**，PowerShell 会失败 | 统一 Git Bash，显式追加 `$HOME/.bun/bin` 到 PATH |
| 2 | **管道会吞掉真实退出码** | 判断门禁结果时先重定向再读码，不要接管道 |
| 3 | 校验工具**判定失败时退出码仍为 0** | 必须读状态行，不可依赖退出码 |
| 4 | `codex exec` 读 stdin 会**回显整个提示词**淹没响应 | 提示词落盘后按标记提取，注意取最后一次出现 |
| 5 | **高推理档下推理过程占满输出**导致答复被截断 | 结构化任务显式降档 `medium` |
| 6 | **三套安装版本不同**（1.58.3.0 / 1.87.3.0 / 1.91.121.0） | 固定用 `~/.codex` 1.91.121.0，写进 ENVIRONMENT.md |
| 7 | **`claude-available.json` 是假信号** | 只代表"装了 claude CLI"，必须实跑派发验证 |
| 8 | **codex 路径哈希会随升级变** | 不要写死；用 `where codex` 解析 |
| 9 | spawned 模式下**模型会编理由跳过门** | 复核它"我做不到"的理由；关键门禁保持 interactive |
| 10 | 第一梯队真实性行**标 `n/a` 被判 missing** | 不许用"不适用"绕过必做校验 |
| 11 | 无凭据的行**不算行** | 凭据须为 `路径:行号` 或提交哈希 |
| 12 | `/cso` 的 launcher **是协调器而非扫描器** | 安全发现须走完整链路后 `submit` |
| 13 | WSL2 **读不到 OneDrive 路径**下的文件 | 先复制到 WSL 可访问位置 |
| 14 | 管道接 `node` 启动长驻服务**会终止进程** | `Start-Process` + `-RedirectStandardOutput` |
| 15 | PowerShell 的 `npm.ps1` 把 `npm test` 误解析为 `pm` | 文档给不依赖 shell 包装的命令形式 |
| 16 | bash 嵌套引号 + Windows 路径**极易出错** | 脚本写入文件再执行 |
| 17 | 被中断任务留下**孤儿 node 进程** | 重启前先清理，端口冲突时尤其明显 |
