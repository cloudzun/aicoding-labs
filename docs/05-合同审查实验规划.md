# ③ 合同审查实验规划（待批）

> **定位：** 三个案例的第三棒。① 考"能不能承认不知道"，② 考"能不能守住边界"，③ 考**"能不能分级与追溯"**——机器给风险等级与证据，人做最终判断。
> **与前两个的根本差异：** ①② 的正确答案都能由代码算出（引用/EX）；③ 的"风险"是**主观判断**，所以 ③ 必然重新依赖 LLM 与人工——这恰好用来检验前两轮沉淀的经验能不能迁移。

---

## 一、目标与不做

### 1.1 目标（客户验收表原值）

| 客户指标 | 我们的口径改写 |
|---|---|
| 核心风险识别召回 ≥88% | 分母从"合同"改成**"规则×合同判定单元"**（27 规则 × 30 份 = 810 单元），否则 ±14pp 测不出来 |
| 10 页合同 ≤10s | 规则引擎（确定性）秒级 + 语义规则分片并行；LLM 只跑语义型规则 |
| 风险分级 | 高/中/低三级，映射表写死，等级一致率单独报 |
| 结构化报告 | 固定 schema：定位（页/段/偏移）+ 规则 + 等级 + 原文引用 + 修改建议 |
| 必查项 vs 建议 | **存在型（该有的没有）** 与 **风险型（有的但不利）** 分开报 |

### 1.2 不做

- ❌ 不做法律意见（只做"清单式检查 + 提示"）
- ❌ 不做合同生成、不做谈判建议
- ❌ 不承诺 PDF 扫描件 OCR（与 ① 一致）
- ❌ 不做多份合同比对（v1 单份）
- ❌ 不替代人工签署流程

## 二、数据方案（30 份合成合同 + 12 类植入缺陷）

### 2.1 为什么自建

与 ② 同理：**只有自建才能保证"标准答案"存在**。真实合同涉敏且无法标注；公开合同数据集许可不明、条款体系与国内政企不符。

### 2.2 合成方式

- 用 `python-docx` 模板生成，变量化：甲方/乙方、金额、期限、付款节点、违约金比例、管辖法院、知识产权归属、保密期限。
- 3 种合同类型 × 10 份：**采购合同 / 服务合同 / 框架协议**（覆盖政企常见三类）。
- 其中 6 份正常（对照），24 份各植入 2–5 处缺陷。

### 2.3 12 类植入缺陷（对应规则）

| 编号 | 缺陷 | 类型 | 判定方式 |
|---|---|---|---|
| D01 | 缺保密条款 | 缺失型 | 存在性检测（关键词+章节号） |
| D02 | 违约金比例低于 0.3‰/日 | 数值型 | 代码计算 |
| D03 | 付款周期超过 60 天 | 数值型 | 代码计算 |
| D04 | 单方无责解除权 | 语义型 | LLM + 证据 |
| D05 | 自动续期且无提示义务 | 语义型 | LLM |
| D06 | 责任上限缺失或无限责任 | 语义型 | LLM |
| D07 | 管辖地在对方法院所 | 语义型（实体抽取） | 规则+LLM |
| D08 | 知识产权归属约定模糊 | 语义型 | LLM |
| D09 | 缺发票/税率条款 | 缺失型 | 存在性 |
| D10 | 缺 SLA/服务标准 | 缺失型 | 存在性 |
| D11 | 数据合规/个人信息条款缺失 | 缺失型 | 存在性 |
| D12 | 签署主体与盖章页信息不一致 | 结构性 | 代码 + 规则 |

### 2.4 数据契约（每份合同的标注）

```json
{"contract_id":"CT-001","type":"采购合同","pages":8,
 "units":[{"rule_id":"R02","present":true,"risk":true,"level":"高",
           "locator":{"page":3,"para":7,"char_offset":412},
           "evidence":"违约金按合同总额的0.1‰/日计算","expected":"不低于0.3‰/日"}]}
```

## 三、规则引擎设计（双引擎）

### 3.1 规则 DSL（YAML，27 条）

```yaml
- id: R02
  category: 数值型            # 存在型 / 缺失型 / 数值型 / 语义型 / 结构性
  severity_default: 高
  detector: deterministic     # deterministic | llm | hybrid
  scope: 违约责任条款
  check: "违约金日费率 >= 0.3‰"
  evidence_required: true
  remediation: "违约金比例建议不低于合同总额的0.3‰/日"
```

### 3.2 分工（关键设计）

| 类型 | 谁来判 | 为什么 |
|---|---|---|
| 数值型 / 结构性 / 存在型 | **代码**（正则 + 数值解析 + 章节匹配） | 确定性、零延迟、可测 |
| 语义型（责任对等、定义清晰、单方权利） | **LLM + 强制引用原文** | 只能靠语义，但必须给证据 |
| 缺失型 | **先存在性检测，再 LLM 兜底** | 通用模型对"缺失"系统性弱，不能纯 LLM |

**硬约束：LLM 不得新增规则**（规则白名单），只能对给定 rule_id 判定。这条直接来自 BP-6。

### 3.3 报告 schema（固定）

```json
{"contract_id":"CT-001","summary":{"高":3,"中":5,"低":2,"必查缺失":4},
 "findings":[{"rule_id":"R02","level":"高","title":"违约金比例过低",
   "locator":{"page":3,"para":7},"evidence":"...原文...",
   "remediation":"..."}],
 "coverage":{"rules_checked":27,"rules_skipped":[]},
 "meta":{"model":"...","rule_version":"1.0.0","elapsed_ms":8420}}
```

### 3.4 安全与合规

| 风险 | 对策 |
|---|---|
| 文档提示注入（合同里写"忽略以上指令"） | 文档内容**只作数据**、加分隔符与角色隔离；LLM 输出必须过 schema 校验 |
| 大文件 | 上传 ≤10MB、≤50 页；分片处理 |
| 原文外泄 | trace 只存定位与引用片段（≤200 字），不存全文 |
| 云端处理 | 页面固定披露（与 ① 同） |

## 四、评测设计（三套，都进 CI）

| 套件 | 规模 | 判定 | 门槛 |
|---|---|---|---|
| **规则命中集** | 810 单元（27×30） | 自动比对（存在/风险/等级） | 存在型 P≥85% / R≥88% / F1≥85%；缺失型 R≥85% 且误报率 ≤15% |
| **报告质量集** | 30 份 | 结构校验（定位可回查、引用原文一致、等级合法） | 100% 通过 |
| **人工锚点集** | 20 份（10 正常 + 10 含缺陷），人工标注 | 与系统判定对比 | 一致率 ≥85% |

**关键：召回必须成对报精确率**，否则等于奖励"全都标红"（① 的教训）。

**尺子自检（BP-2，必须前置）：**
- judge 自检集 10 条（人工已知"是否构成风险"）→ 必须 10/10；
- 定位回查器单测 5 例（页/段/偏移偏移 1 位应报错）。

## 五、八环适配（与 ①② 的差异）

| 环 | ①② 的做法 | ③ 的做法 | 差异原因 |
|---|---|---|---|
| 0 数据与口径 | 库/语料 + 指标改写 | **规则清单确认 + 判定单元定义 + 尺子自检集** | 规则是主观的，必须先定 |
| 3 会审 | 工程 + 合规两声音 | **工程 + 合规 + 法务**三声音 | 风险等级需专业判断 |
| 4 施工 | 检索/生成 | **解析 → 规则引擎 → LLM 语义层 → 报告** | 双引擎结构 |
| 5 题库 | 从 gold 反写问句 | **从缺陷植入记录直接生成标注** | 合成数据自带标注 |
| 6 QA | EX / 功能 | **规则命中 + 定位回查 + 注入防御** | 两类新风险 |
| 8 复盘 | 指标拆解 | 指标拆解 + **人工一致率分析** | 主观指标必须有人的锚 |

## 八、风险 Top 5

| 风险 | 影响 | 对策 |
|---|---|---|
| 规则清单主观、客户不认 | 验收争议 | 环 0 就让客户确认规则表；每条给"判定依据" |
| 缺失型检测天花板 | 召回上不去 | 存在性检测（章节+关键词+编号三重）+ 白名单式"应有条款域" |
| PDF 解析质量 | 定位不准 | v1 以 docx 为主，PDF 只做 2 份冒烟并如实标注 |
| judge 依赖回升 | 重蹈 ① | 强制前置 judge 自检集；语义规则必须有原文引用 |
| 涉敏 | 不能进客户环境 | 全程合成数据；页面披露"云端处理" |

## 九、需要你先拍的三件事

1. **规则清单从哪来**：用我按业界实践整理的 27 条（`docs/ref/scenario-contract.md` 已有 YAML 草案），还是你提供客户真实清单？
2. **判定单元口径**：按"规则×合同"（810）还是"规则×条款片段"（更细但标注成本翻倍）？我建议前者。
3. **合同类型**：采购/服务/框架三类各 10 份，还是聚焦一类做深（比如只做服务合同）？我建议三类，因为"通用性"是课程要展示的。

> 以上三项确认后即可开工；若你只想先看效果，我也可以先做 D1（口径+数据生成器），产出 30 份合同和 810 单元标注给你验。
