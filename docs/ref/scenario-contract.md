# 合同审查 AI · 业界实践调研与可复用规则清单

> **场景**：明州数智教学 demo（demo3）——上传 Word/PDF，按规则清单识别风险与缺失项，输出风险分级的结构化审查报告。
> **客户验收指标**：核心风险召回 ≥88%、10 页以内单份 ≤10 秒、风险等级标注、结构化报告。
> **调研日期**：2026-10-20　**调研人**：contract-review（AI 应用研究员）
> **结论强度标注**：✅ = 已打开原文核对 ｜ ⚠️ = 厂商自述/营销口径，未第三方验证 ｜ 🔧 = 工程推断，无公开来源

## 0. 三条结论先给

### 结论一：88% 召回"分口径看"——宽口径不现实，窄口径现实但必须先锁口径

| 口径 | 88% 召回是否现实 | 依据 |
|---|---|---|
| **宽口径**：任意商业合同、开放条款类型（CUAD 41 类）、未见过的真实合同、严格 span 覆盖判定 | ❌ **不现实**。公开最优专用模型在 80% 召回时精度只有 44.0%，推到 90% 召回精度崩到 17.8% | CUAD 论文 DeBERTa-xlarge 结果 ✅ |
| **中口径**：单一合同类型（如电信采购/服务类）、20–30 条自建规则、30–50 份同质化合同 | 🟡 **可达但需架构支撑**，且要把"存在型风险"与"缺失型风险"分开报 | ContractEval + LegalOn 失效模式 ✅ |
| **窄口径**：仅"核心风险"子集（10–15 条高确定性、可正则/数值判定的规则）、评测集与规则同源 | ✅ **现实**（甚至可到 90%+） | 🔧 工程推断 + 国内产品宣称口径 ⚠️ |

**关键风险点**：客户说的"核心风险召回≥88%"目前**没有定义分母**。同一个系统，换一种召回定义，数字能从 62% 跳到 95%。这不是技术问题，是验收合同问题——必须在开工前把它写死（见 §3.4 的验收模板）。

### 结论二：业界主流不是"纯 LLM"，也不是"纯规则"，而是 **harness（规则编排 + 单点 LLM 判定）**

三家最直接的证据：
- LegalOn 明确把架构叫 "harness"：不是让一次模型调用审全篇，而是**约 21–25 个聚焦检查并行，每个检查只隔离到"单条规则 + 单条条款"**，因此做到单份 2.3 秒，而通用模型单遍通读需 40.4 秒（17 倍差距）。并且它点名通用模型的五类系统性失效，其中最致命的一类就是**缺失检查（absence check）**——正是"缺失项识别"。✅
- 华宇元典把审查引擎拆成"**审查项分级引擎 + 审查方法引擎**"，方法分三种：自然语言规则审查、要素结构化审查、**代码审查**（数值比较交给代码，不交给模型，例如"分期付款之和是否等于合同总价"）。✅
- Spellbook 把审查分成两个 tab：**Playbooks（规则，逐条 Pass/Fail/Fallback）+ Questions（问答）**，并支持 Standard Review / Redline Review 与轻/标准/重三档审查深度。✅

**对客户的直接结论**：demo 的卖点不该是"大模型能读懂合同"，而该是"**一份可维护、可审计、可解释的规则清单 + 每条规定性检查的确定性执行**"。LLM 只负责它擅长的部分（语义是否等价的判断、改写建议生成），数值、比例、期限、管辖法院、是否出现某关键词，全部用代码。

### 结论三：10 页 ≤10 秒——文本型可行，扫描件不可行；必须拆成两个时延指标

- 公开可对标的端到端速度：LegalOn 单份 2.3 秒（未披露页数）⚠️；木瓜合同宝宣称"百页合同 3 分钟"≈ **1.8 秒/页** ⚠️；Claude Opus 4.6 单遍通读单份 **40.4 秒** ✅（LegalOn 实测）。
- **10 页 ≤10 秒 = 1 秒/页**，比公开可对标的 1.8 秒/页还要快近一倍。纯靠"更强的模型"做不到，只能靠**架构省算力**：规则前置过滤 + 只对候选条款调模型 + 小模型 + 规则级并行。
- **扫描件（需 OCR）基本不可能进 10 秒**，除非有 GPU OCR 且接受降采样。建议合同里就把"解析方式"作为时延指标的分档条件。

**建议改写验收指标为**：
- **T1（首屏可读）**：≤10 秒 —— 解析完成 + 高风险项与风险清单骨架先出（流式）。
- **T2（完整报告）**：≤30 秒 —— 全部规则判定 + 修改建议 + 可导出审查意见书。
- **扫描件**：T1 ≤20 秒 / T2 ≤60 秒，或明确排除在 10 秒口径外。

### 1.2 商业侧：从"标红"到"playbook 编排"

**行业痛点数字**（LegalOn 2025 State of Contracting 调查，286 名法务）✅：
- 法务团队审一份合同平均 **3.2 小时**
- 年处理 500 份合同 = **1,600 小时 = 200 个工作日**
- AI 用于合同审查的采用率**同比增长 75%**
- **95% 的团队自认 playbook 覆盖有缺口，54% 根本没有 playbook**

最后这个数字很重要：**"规则清单从哪来"在业界本身就是个未解决问题**。卖"我们帮你把规则清单建起来"比卖"我们的模型更强"更打动人。

**Harvey**（面向顶级律所）的做法值得借鉴：playbook 不是让律师一条条填表，而是**从"你已有的 playbook / 已签合同 / 标准模板 / 对话"里自动提炼规则，边生成边侧边栏预览**；它把 playbook 定性为 "living artifact"（活文档）而不是静态配置，并声称已沉淀 300+ 客户 playbook 的方法论。✅ 引用 EY Law 的数据：合同团队 **40% 以上时间**花在常规低复杂度合同工作上。✅

**Spellbook**（Word 插件形态）的审查 UX 值得借鉴 ✅：
- 两个 tab：**Rules**（逐条通过/失败）+ **Questions**（问答，答案带编号气泡可跳原文）
- 每条规则点进去能看到"为什么通过/失败"的摘要 + 引用，还能点 **Show Rule** 看规则原文（可解释性做到规则级）
- 失败规则给 **Add Language** 建议文本，可 Regenerate / Ask for Changes / 手动 Edit / Insert at Cursor
- 有 Fallback（退让方案）状态——**这是 playbook 的精髓：不是"合规/不合规"二元，而是"首选条款/可接受退让/红线"三档**
- 导出：playbook 摘要可下载或邮件分享

### 1.3 机制之争：规则清单 vs 纯 LLM —— 业界答案是"都不是，是 harness"

**证据链**：

1. **LegalOn 的失效模式分析**（最有价值的一段）✅。它对比 LegalOn vs 11 个通用模型（含 Claude Opus 4.6、Gemini 3.1 Pro、GPT-5.1），3,282 次头对头评审、21 条"精度关键"指引，总结出通用模型五类系统性失效：

   1. **具体条款识别**：能识别"话题"但抓不住"精确措辞"（如"无需对方同意即可转让"里的"无需同意"限定语被忽略）
   2. **数值阈值检查**：确认了条款存在但不核验内嵌门槛（如租金涨幅 ≤150%、保证金 ≤3 个月）
   3. **交叉引用校验**：SOW 是否引用 MSA 条款、保密目的是否被明确定义
   4. **多条件要求**：由 "AND" 连接的多个独立条件，模型满足其一就判"已满足"
   5. **缺失检查（absence check）**：**"通用模型被训练去找'有什么'，它们在确认'应有而确实没有'时不可靠"**

   原文建议的应对就是 **harness**：把合同拆成结构化、条款级的检查，**每次模型调用只隔离到一条规则 + 一个条款**，逐条比对精确标准。

2. **华宇元典的双引擎** ✅：审查项分级引擎（决定查什么、多严）+ 审查方法引擎（决定怎么查）。三种方法：
   - **一般规则审查**：自然语言描述风险规则
   - **要素审查**：先结构化抽取关键事实（如"验收后 5 个工作日付全款" vs "验收且收到发票后 30 个工作日付全款"），再把抽取结果喂进规则
   - **代码审查**：数值计算（如分期付款之和是否等于总价）交给代码
   
   并明确提出 **L0–L4 分层审查清单体系（通用 + 类型化 + 个性化）**，支持企业上传自有范本与风险条款库——这就是"把企业立场编码成可维护规则"的工程答案。

3. **法大大 iTerms Pro** ✅：
   - "审查清单智能构建：能够根据用户的合规文件要求学习训练，形成更加符合公司要求的审查逻辑"
   - "可选不同**审查立场和尺度**"（对应甲方/乙方/中立，与通义法睿的 position 参数一致）
   - "审查意见：包括**风险等级和风险类型**，附带交易解析、主体尽调"
   - "超 20+ 合同类型、2000+ 合同范本、**5000+ 条审查条款**数据沉淀"
   - 导出四件套：**批注版 / 修订版 / 清洁版 / 审查意见书**
   - 自研垂类模型已**通过国家网信办算法备案**（央企/运营商客户的关键合规项）

4. **幂律智能 MeCheck** ✅："基于完备法律知识图谱构建、海量数据标注与训练……**在一分钟内实现数百个合法性、合规性风险点的排查和提示**"——注意"数百个风险点"与"一分钟"是同框出现的，说明国内产品的默认形态就是**大规则库 + 快速扫描**，不是开放式对话。

5. **上海百事通（百小通）** ✅："以 RPA+AI 为核心驱动，搭建'**经验引擎 + 规则引擎 + 调度引擎**'三重架构"。"经验引擎"这个命名本身就是答案：**规则清单不是凭空写的，是把资深律师的审查经验显性化、结构化的产物**。这和 LegalOn 的"135+ 律师构建 playbook"、Harvey 的"从 300+ 客户 playbook 提炼方法论"是同一件事的三种说法。

> **对我们的启示**：规则清单的权威性来自"**谁写的 + 怎么维护的**"，而不是"有多少条"。demo 里如果能把规则的来源标注出来（"本规则由××律所合伙人基于《民法典》第585条与集团 2024 年采购制度制定，v1.2 于 2026-09 修订"），可信度会远高于"我们的模型在 CUAD 上 F1 0.64"。

**规则库规模对标**（做设计时的量级参照）：

| 产品 | 规则/条款库规模 | 合同类型覆盖 |
|---|---|---|
| 法大大 iTerms Pro | 5000+ 条审查条款，2000+ 范本 | 20+ 类型 |
| LegalOn | 135+ 律师构建 playbook，10,000+ 法律问题 | 常见商业合同全覆盖 |
| 通义法睿 | 规则由模型按合同+立场动态生成（也可传入自定义规则） | 通用 |
| **我们的 demo** | **27 条**（demo）→ 80–120 条（试点） | **1–2 类（电信采购/服务）** |

→ 结论：**demo 阶段绝不要拼规则数量**。20 条打透比 200 条糊弄更有说服力。用"规则可维护、可审计、可解释"作为差异点。

**如何把"企业立场/偏好条款"编码成可维护规则**——LegalOn 给的写法规范可直接抄 ✅：

| 原则 | ❌ 反例 | ✅ 正例 |
|---|---|---|
| 说清"必须包含什么"，不要用模糊形容词 | "审查违约责任是否合理" | "合同必须包含 24 小时数据泄露通知义务" |
| 具体、给数值 | "合同应有合理的责任上限" | "总赔偿责任上限不得超过合同金额的 2 倍" |
| 一条规则只说一个问题 | "确保 NDA 覆盖保密、专有信息和不竞争" | "保密信息必须包含口头披露" |

LegalOn 还给了"先建哪 8 条"的起步清单（**Great 8**）：知识产权、责任限制、赔偿（indemnification）、保密信息、数据保护与安全、保证（warranties）、付款条件、终止后果。✅ 这 8 条与我们要写的电信采购规则高度重合，可直接作为规则库 v0 的骨架。

### 1.4 风险分级与报告字段

**层级定义（国内三家口径高度一致）**：

| 产品 | 等级体系 |
|---|---|
| 通义法睿 API | `riskLevel`: **high / medium / low**（规则级与结果级各一个）✅ |
| 法大大 | **风险等级 + 风险类型**，再叠加交易解析、主体尽调 ✅ |
| 华宇元典 | **L0–L4 分层审查清单** + "审查项分级引擎" ✅ |
| LegalOn | 按 **severity 排序**而非平铺列表；"thresholds you can calibrate to your risk tolerance" ✅ |

**通义法睿的完整字段设计（直接可复用的行业标准）** ✅：

规则生成接口（`RunContractRuleGeneration`）：
```
position     审查立场：0=中立，1=甲方，2=乙方
rules[]:
  riskLevel    high / medium / low
  ruleSequence "1.1"               规则序号（支持两级编号）
  ruleTag      "审查条款的合法性"    规则标签（类型）
  ruleTitle    "审查该合同标的条款中，标的合法性相关的风险"
Usage: 按页计费（unit=page，input=文档页数）
```

结果生成接口（`RunContractResultGeneration`）：
```
result:
  examineBrief   审查结果概述（一段话）
  examineResult  审查结论（"需要修改"）
  riskLevel      high / medium / low
  ruleSequence / ruleTag / ruleTitle   ← 回溯到规则，可解释性来源
  subRisks[]:
    riskClause               风险条款名称（"不可抗力条款"）
    riskExplain              风险点说明（"未明确法定免责情形—不可抗力"）
    riskBrief                风险简述（"未定义不可抗力及其后果，可能导致…"）
    originalContent          风险项对应的合同原文（★ 定位）
    resultContent            修改后文本（★ 修改建议，直接给可用条款全文）
    resultType               需修改 / 需删除 / 需新增 / **通过**
    standardOriginalContent  合同比对模式下才有（★ 与标准范本对照）
```

**这张表几乎就是一个完整的 demo 报告字段清单**，而且 `resultType` 里显式有"**需新增**"——即**缺失项是一等公民**，不是补丁。这一点必须写进我们的报告 schema。

### 1.5 评测口径：precision/recall 在法律场景里怎么被定义

**CUAD 的定义**（最权威，可引用）✅：
- **TP** = ground truth 的段落有匹配预测；**FP** = 预测没匹配上任何 ground truth 段落；**FN** = ground truth 段落没被匹配
- **匹配判据**：Jaccard 相似度 ≥ **0.5**（去标点、转小写、按空格切词后计算）
- 预测带置信度 → 扫阈值得到 **PR 曲线** → 报 **AUPR** 和 **Precision @ X% Recall**
- 动机：条款只占合同约 **10%** 文本，单个标签平均只占 **0.25%**，极度不平衡，所以用 P/R 而非 accuracy

**ContractEval 的定义**（更严格，也更接近"报告准不准"）✅：
- **TP**：label 非空，且模型预测**完全覆盖**标注 span
- **TN**：label 为空，模型正确回答 "no related clause"
- **FP**：label 为空，模型却输出了非空条款
- **FN**：label 非空，模型回答 "no related clause" **或未完全覆盖** label span
- 额外指标：**F2**（更看重召回，因为漏检后果更重）、**Jaccard 平均**（输出是否冗长）、**"lazy" 误报率**（有条款却答"无相关条款"的比例）

**注意这个"完全覆盖"判据**：同一套模型，用"命中即算"和"完全覆盖才算"，TP 数能差 10–20 个百分点。**验收时这一句必须写清楚**。（🔧 工程推断，基于两个基准的 TP 定义差异）

**CUAD 论文的"人怎么读这个数字"** ✅：在 80% 召回时精度 30% 意味着"**律师每看到 1 条相关条款，要额外读 22 条不相关的**"。这是把技术指标翻译成业务代价的标准说法，汇报时很好用。

### 1.6 解析链路：Word/PDF/扫描件的坑

来自合合信息 TextIn 的长文档解析实践（国内做文档解析最成熟的团队之一）✅：

**痛点排序**（原文明确说"最常见的问题不是 OCR 识别率，而是怎么切、怎么存"）：
1. **结构丢失**：章、节、条、附录、表格、图片的关系被冲平
2. **粒度失衡**：整块太长不利于召回，切太碎又丢上下文
3. **噪音混入**：**页眉页脚、页码、侧边注释**污染条款块
4. **表格图片失联**：表格被当普通文本旁的附属物
5. **难以溯源**：检索命中后无法确认对应原文哪一页、哪一块

**推荐的链路架构**（"文档解析 + 确定性后处理"，明确反对一开始就让大模型接管全流程）✅：
```
文件上传 → 文档解析 → detail 级结构化结果 → 目录构建 → 分块
        → 媒体提取 → 溯源映射 → 入知识库/检索/LLM 应用
```
理由："标题层级、caption 归属、页码和位置映射，本质上更适合**确定性逻辑**；如果一开始就把整条链路交给模型，基础结构不稳和模型输出不稳会叠加，系统很难调试。"

**具体可抄的做法** ✅：
- **标题栈驱动分块**：维护 `heading_stack`，遇标题更新栈，标题单独成块，正文追加到当前标题块；每块携带 `title / path / page / text / type`
- **表格独立成块**，表题并入表格块；图片独立成媒体项，caption 紧邻关联
- **页眉页脚出双版本**：`chunks`（去页眉页脚，用于条款检索）+ `chunks_with_paratext`（保留，用于原文复刻），下游按需选，**而不是重新 OCR**
- **每个块必须带溯源元数据**：页码、章节路径、原始 detail 索引、位置映射

**对合同场景的补充坑**（🔧，基于条款结构特征）：
- **条款编号体系混用**："第X条 / X.X / （一）/ 1) / 一、" 常在同一份合同里混用，且**附件/补充协议会另行编号**，靠单一正则必翻车 → 需要"编号家族"识别 + 上下文校验
- **跨页条款**：一条主条款横跨 2–3 页，页脚页码插在句子中间；若按页切块会把一句话劈开 → 拼页时必须用"句末标点 + 编号连续性"双重判断
- **表格里的条款**：付款结构、SLA 指标、交付清单常在表格里，OCR 后行列对齐错乱 → 表格必须走独立的表格解析通道（`pdfplumber` / 版面模型），不能当纯文本
- **修订痕迹/批注**：Word 的 `w:ins` / `w:del` 若不清洗，会抽出重复甚至矛盾的条款文本
- **扫描件倾斜/印章遮挡**：中文合同右侧骑缝章、骑缝线常压字
- **金额大写小写不一致**：这本身是一条规则（见 §5 的 R05），但会同时是解析问题

### 1.7 性能拆解：10 页 ≤10 秒怎么算

**公开可对标的时延数据**：

| 来源 | 数字 | 条件 | 可信度 |
|---|---|---|---|
| LegalOn 2026 基准 | **单份完整审查 2.3 秒**；Claude Opus 4.6 单遍通读**单份 40.4 秒** | 合同页数未披露；LegalOn 约 21–25 个条款级检查并行 | ⚠️ 厂商自测 |
| 木瓜合同宝（长江日报报道） | **百页工程合同 3 分钟**（≈1.8 秒/页），人工 2 个工作日 | 含 37 项风险提示生成 | ⚠️ 媒体转述厂商 |
| 木瓜合同宝 | 单份租房合同**不到 1 分钟**，自动生成 20 余项风险提示，每条标明修改建议和法规出处 | 小程序场景 | ⚠️ 同上 |
| vLLM + Qwen2.5-72B-AWQ on 单张 L20 48GB | **聚合 108.84 output tok/s @并发10**；p95 TTFT **6.61 s**；p95 端到端 **23.54 s**（固定 512 入/256 出） | 24 小时压测，36,740 请求零失败 | ✅ 学术报告 |

- 也就是说：**"一次全文调用生成完整报告"在 10 秒内绝无可能**（2,000 token 的 JSON 输出 ≈ 100–180 秒）

**10 页合同的分阶段预算（文本型 DOCX/电子 PDF）** 🔧：

| 阶段 | 耗时估算 | 说明 |
|---|---|---|
| 文件接收 + 类型识别 | <0.1 s | |
| 解析（docx / 电子 PDF） | **0.1–0.5 s** | `python-docx` / `PyMuPDF` 逐页抽文本+坐标；10 页约 8k–15k 汉字 |
| 条款结构化（标题栈 + 编号正则 + 表格独立通道） | **<0.1 s** | 纯 CPU，确定性逻辑 |
| 确定性规则（数值/比例/期限/关键词/存在性，约 10–14 条） | **<0.1 s** | 代码执行，不经模型 |
| 语义规则（LLM，8–12 条 × 单条调用） | **4–7 s** | 关键：并发 8 路；每条输入仅"候选条款片段 + 1 条规则"约 800 tok，输出 ~150 tok |
| 汇总/去重/分级/渲染报告 | <0.2 s | |
| **合计（T2 完整报告）** | **≈5–8 s** | ✅ 可达标 |
| **T1 首屏（骨架 + 高风险项）** | **≈1.5–3 s** | 流式返回，达标留有余量 |

**扫描件（需 OCR）** 🔧：
- CPU OCR（PaddleOCR 类）10 页：**3–10 s**，视分辨率与版面复杂度
- 结论：扫描件 T1 ≤20 s / T2 ≤60 s，或**明确排除在"10 页 ≤10 秒"之外**

**容量规划推论** 🔧：若并发用户 >3，单卡 70B 不够。要么加卡，要么换 14B/8B 级别模型（吞吐高 5–10 倍，但 ContractEval 显示 Qwen3 8B thinking 的 F1 只有 0.540 vs GPT-4.1 的 0.641，掉 10 个百分点）。**demo 用 API，试点再谈本地化**——但要提前跟客户对齐"数据不出网"是否硬约束（法大大、央企客户是硬约束，运营商大概率也是）。

## 3. 评测口径与可对标水平

### 3.1 "核心风险召回"至少四种可能的定义，差别巨大

| 定义 | 分母 | 判定单位 | 88% 难度 |
|---|---|---|---|
| **D1 文档级** | 每份合同是否检出了该合同的全部真实高风险项 | 合同 | 最宽松也最不稳定（一份 5 个风险漏 1 个就算失败） |
| **D2 风险实例级** | 标注出的每个风险实例（span）是否被检出 | (合同, 风险, span) | **最推荐**：与 CUAD/ContractEval 口径一致，可对标 |
| **D3 规则级** | 规则清单中每条规则在每个合同上的判定是否正确（含"正确判为通过"） | (合同, 规则) | 包含"缺失项"判定，**最难** |
| **D4 仅存在型风险** | 只看"有风险条款被找出来"，不看"应有条款是否缺失" | (合同, 规则) | 最容易，可到 90%+ |

**两个必须注意的结构性事实**：

1. **ContractEval 里最差的是哪几类？** "Uncapped Liability"（无上限责任）、"Joint IP Ownership"（共同知识产权）、"Notice Period to Terminate Renewal"（续约终止通知期）——**F1 接近 0**。而这三类恰好是**高商业风险条款**。原文原话：*"these clauses are important and of high risks in real life"*。✅ 也就是说：**公开基准上，模型在"简单常见条款"能做到 F1 0.9（如 Governing Law、Parties），但在"珍稀且高价值条款"上几乎归零**。这直接决定了 88% 召回的分母里不能混进这类。
2. **ContractEval 总体结论**：*"most LLMs perform at a level comparable to junior legal assistants"*（多数 LLM 相当于初级法务助理水平）。这句话是最适合放进汇报的预期锚点。✅

### 3.3 "88% 召回"现实吗——判断依据

#### 判断一：在公开基准口径下（D2 + CUAD 41 类 + 未见过的合同），88% 召回不现实

依据：
- CUAD 上最强专用模型 DeBERTa-xlarge 在 80% 召回时精度仅 44.0%，推到 90% 召回精度只剩 17.8%（✅ 论文表 2）。这意味着**在 90% 召回这个点上，系统每报 5 条，只有 1 条是对的**——业务上不可用。
- ContractEval 上最强商用模型 GPT-4.1 的 F1 只有 0.641（✅ 严格"完全覆盖"判定）。若 P≈R≈0.64，召回约 64%，距 88% 差 24 个百分点。
- 论文作者自己的判断：CUAD 的 "80% recall may already be reasonable for some lawyers"（✅ 原文）——即**业界认为 80% 召回已经算可用**，没人把 90% 当基线。
- **没有任何一家厂商公开发布过"CUAD 口径 88% 召回"的数字**。厂商发布的都是自建基准上的头对头偏好率（ELO / preference rate），不是召回率。这是个强烈的负面信号：**如果容易做到，早就宣传了**。

#### 判断二：在窄口径下（D3/D4 + 自建 20–30 条规则 + 同质化合同），88% 可达

依据（🔧 工程推断，但每一步都有公开事实支撑）：
- 分母缩小：27 条规则 × 30 份合同 = 810 个判定单元 → 单条规则的样本量足够做统计
- 判定可操作化：约 10–14 条规则可退化为**确定性检查**（正则、数值比较、存在性、比例求和），这类检查的召回本质是 100%（除非解析出错）——把"确定性规则"计入分母，整体召回会被显著拉高
- 同分布：电信采购/服务类合同的条款写法高度相似，规则命中率高
- 有"须新增"（缺失）判定的部分可单独拆出来，不拖累整体

**但必须接受的代价**：精度会掉。CUAD 的 P@80%R = 44% 告诉我们，召回推到 80%+ 时**精度往往只有 40–50%**。所以验收指标必须**成对出现**（如"召回 ≥88% 且 精度 ≥60%"），只考召回等于鼓励系统乱报。

#### 判断三：如果是"含缺失项的 D3 口径"，88% 是本任务最大的技术风险

依据：LegalOn 明确把 **absence check（缺失检查）** 列为通用模型的第五类系统性失效，原话：*"General-purpose models are trained to find what is there. They are not reliable at confirming when something required is definitively absent."* ✅ 而且它列了 5 个失败案例中就有 3 个是缺失型（PHI 所有权未明示、NDA 未定义目的、续约通知期未约定）。

**对策**（写进方案）：
- 缺失项**不走纯 LLM**。用"结构性存在性检查"：先建立"本合同应有的条款域清单"（27 条规则 → 27 个条款域），再判断每个域在合同中**是否存在对应条款**（关键词 + 编号 + 语义一次校验）。存在性判断可做到高确定性。
- 缺失项与存在型风险**分开统计、分开报数**。文档里明确："存在型风险召回 X%，缺失型风险召回 Y%"，而不是一个混合的 88%。

### 3.4 建议的验收方案（可直接写进合同附件）

**① 口径必须写死的 9 项**

| # | 项 | 建议取值 |
|---|---|---|
| 1 | 召回定义 | D2 风险实例级（存在型）与 D3 规则级（缺失型）**分开报** |
| 2 | 匹配判据 | 条款定位与标注所在条款编号一致，或 Jaccard ≥ 0.5（沿用 CUAD 判据） |
| 3 | 评测集 | 30–50 份真实脱敏合同，**与规则清单同源**（同一批业务方提供） |
| 4 | 标注 | **双人独立标注 + 第三人仲裁**（CUAD 是 3 人复核，我们降一档但必须 ≥2 人） |
| 5 | 分歧处理 | 两人不一致且仲裁后仍不确定的样本 → **从分母剔除**，并在报告中披露剔除数 |
| 6 | 规则子集 | "核心风险"= 规则清单中标记为 P0 的 10–15 条，**评测前书面锁定，不得赛后调整** |
| 7 | 时效 | T1 首屏 ≤10 s、T2 完整报告 ≤30 s，各测 20 次取 **P95** |
| 8 | 硬件/模型版本 | 写明模型名与版本、是否量化、部署形态（API/本地） |
| 9 | 复现 | 保留 30 份原始文件 + 标注 + 每次运行的原始 JSON 输出，可复跑 |

**② 样本量与置信区间**（🔧 二项分布计算，可直接用于说服客户）

要区分"实测 88%"和"真实 80%"，样本量决定一切：

| 判定单元数 n | 实测 88% 的 95% 置信区间半宽 | 能否与 80% 区分 |
|---|---|---|
| 30 份合同（D1） | ±11.6 pp | ❌ 完全无法区分 |
| 50 | ±8.9 pp | ❌ 勉强不能 |
| 100 | ±6.4 pp | 🟡 勉强 |
| 200 | ±4.5 pp | ✅ 可区分 |
| 810 个规则×合同判定单元（D3） | ±2.2 pp | ✅ 很好 |
| 1500 个判定单元 | ±1.6 pp | ✅ 很好 |

**谈判要点**：如果客户坚持"测 20 份合同达到 88%"，那这个 88% 在统计上毫无意义（置信区间 ±14 pp）。**正确做法是把分母定为"规则实例"而不是"合同"**——27 条规则 × 30 份合同 = 810 个判定单元，置信区间收窄到 ±2.2 pp，且样本采集成本一样。这是本文最实用的一条建议。

**③ Human-in-the-loop 复核流程（业界通行形态）**

各家一致的做法（✅ 综合 LegalOn / Spellbook / 华宇 / 法大大）：
1. **AI 初审**（first pass）：全部规则跑一遍，输出风险卡片
2. **律师逐条处置**：采纳 / 驳回 / 改写；驳回必须选理由（误报 / 风险可接受 / 已线下解决）——Spellbook 的 Dismiss-Apply 二选一就是这个 ✅
3. **回写闭环**：驳回理由聚合为规则调优信号（阈值、例外、白名单）——华宇的"AI 初审 + 对话优化"、Harvey 的 "living artifact" 都是这个意思
4. **抽检**：第三方抽 10–20% 复核一致率，作为"系统可信度"指标而非"准确率"指标

**④ 建议同时考核的"反向指标"**（防止刷召回）

| 指标 | 建议阈值 | 为什么 |
|---|---|---|
| **精度** | ≥60%（存在型）/ ≥50%（缺失型） | 只考召回 = 鼓励全量报风险 |
| **误报"无相关条款"率** | ≤5% | 对应 ContractEval 的 "lazy" 指标；Gemini 2.5 Pro 做到 1.1%，GPT-4.1 是 7.1% ✅ |
| **平均风险条目数/合同** | 落在 8–25 条区间 | 低于 8 条说明漏检；高于 25 条是噪音（木瓜合同宝承包合同 37 项、租房 20+ 项可作参照 ⚠️） |
| **人工复核耗时** | 单份 ≤15 分钟（原始人工 3.2 h 的 8%） | 这是客户真正买单的价值 |
| **定位准确率** | 风险卡片点击后能跳到正确条款，≥95% | 定位错了，整条建议就不可信 |

## 5. 可直接复用的规则清单草案（27 条）

> **适用**：电信运营商**采购类 / 服务类**合同，**甲方立场**（采购方）。
> **免责**：本文为教学 demo 用的规则草案，不构成法律意见；上生产前须经客户法务审定。法条编号以《民法典》为准，建议交付前逐一复核。
> **字段说明**：`判定线索` 是**可执行**的描述（正则/数值/存在性/语义），不是形容词。

### 5.0 规则 DSL 与等级定义

**规则写法三原则**（照抄 LegalOn 规范 ✅）：① 说清"必须包含什么"；② 给数值；③ 一条规则只说一件事。

```yaml
id: PAY-01                    # 域-序号
domain: 付款                  # 条款域
title: 付款节点不得早于验收
position: buyer               # 甲方立场
level: high                   # 规则基准等级 high|medium|low
level_up_if:                  # 上下文升级条件
  - prepay_ratio >= 0.3
level_down_if:
  - has_equal_performance_bond
checker: deterministic        # deterministic | semantic | hybrid
signals:                      # 判定线索
  keywords: [付款, 支付, 价款, 结算]
  regex: ["验收.{0,20}(合格|通过|确认)"]
  numeric:
    - field: prepay_ratio
      expr: "首付款 / 合同总价"
      op: "<="
      threshold: 0.3
  absence:
    - "全文无『验收』字样"
evidence_required: [clause_id, span, page]
suggestion_template: |
  建议修改为：合同生效后甲方支付合同总价的 10% 作为预付款；
  乙方完成全部交付并经甲方书面验收合格、且甲方收到合规增值税专用发票后
  30 个工作日内，甲方支付至合同总价的 100%。
legal_basis:
  - 民法典第509条（全面履行）
  - 集团采购管理制度（待客户提供）
```

**等级定义（三级 + 一票否决）**：

| 等级 | 判定标准 | 处置要求 |
|---|---|---|
| 🔴 **高** | 不修改即签署，将导致**不可承受的损失**（责任无上限、数据合规违规、IP 归属损失、无救济手段）或**违反法律法规强制性规定** | 必须修改，否则不予签署；升级至法务负责人 |
| 🟡 **中** | 损失**可量化**，可通过后续管理/补偿缓解；或己方权利弱于行业惯例 | 建议修改；不接受则需业务负责人书面确认风险 |
| 🟢 **低** | 表述不清、一般性条款瑕疵，不影响核心权利义务 | 可接受，记录在案 |
| ⚫ **否决** | 出现法律禁止性情形（如约定"数据可无限制出境"、约定放弃诉讼权利） | 一票否决，不论金额 |

### 5.1 A 组 · 付款

#### R01 · 付款节点早于验收
- **条款域**：付款 / 验收
- **风险点**：甲方在未取得交付成果前已支付大额款项，丧失付款杠杆；一旦乙方违约，追偿成本极高。
- **判定线索**：
  - 抽取全部付款节点的文本 + 比例，求和校验 = 100%（不等则同时触发 R04）
  - 检查每个付款节点是否关联"验收/验收合格/书面确认"
  - 触发：存在付款比例 ≥30% 的节点，且该节点条件中**不含**验收要素
  - 缺失判定：合同有"付款"条款但全文无"验收"字样 → 直接判高危
- **等级**：高（首付或非验收节点付款 ≥30%）／中（10–30%，或验收表述模糊如"交付验收"未定义）
- **修改建议**：改为"验收合格 + 收到合规发票"双条件付款；预付款比例压至 ≤10%，或要求等额履约保函。
- **依据**：民法典第509条；LegalOn "Great 8" 含付款条件 ✅

#### R02 · 付款比例结构失衡 / 质保金缺失
- **条款域**：付款
- **风险点**：尾款与质保金缺位，交付质量无经济约束。
- **判定线索**：
  - 数值抽取：首付比例、验收后付款比例、质保金比例、质保期长度
  - 触发：`验收后尾款比例 < 10%` 或 `质保金比例 < 3%` 或 `无质保金`
  - 求和校验：`Σ各节点比例 ≠ 100%` → 同时报"付款总额与合同总价不符"
- **等级**：中
- **修改建议**：验收后付至 90–95%，留 5–10% 作为质保金；质保期满且无质量问题后 30 日内无息支付。
- **依据**：行业惯例；华宇"分期付款之和是否等于合同总价"示例 ✅

#### R03 · 发票类型与税率口径不明
- **条款域**：付款 / 税务
- **风险点**：约定"含税"但未写税率与发票类型，进项税抵扣争议；或约定开具普通发票导致无法抵扣。
- **判定线索**：
  - 关键词：`含税 / 税率 / 增值税 / 专用发票 / 普通发票 / 发票类型`
  - 触发：出现金额但**未**同时出现「税率」与「发票类型」；或出现"普通发票"而标的为货物/技术服务
  - 数值校验：合同总价 = 不含税价 × (1 + 税率)，不一致则报"价税合计不符"
- **等级**：中
- **修改建议**：明确"本合同价款为含 13%（或 6%）增值税总价，乙方应开具税率为 X% 的增值税专用发票；发票不合规导致的损失由乙方承担"。
- **依据**：税务合规惯例（🔧）

#### R04 · 逾期付款/逾期交付违约责任不对等
- **条款域**：付款 / 违约责任
- **风险点**：只约定甲方逾期付款的违约责任（如日万分之五），却不约定乙方逾期交付的对应责任，或显著不对称。
- **判定线索**：
  - 分别定位"甲方逾期付款"与"乙方逾期交付/逾期履行"条款
  - 抽取违约金的日利率/比例，做双向对比
  - 触发：`乙方负有逾期违约金约定 == false`，或 `乙方日违约金率 < 甲方日违约金率 × 0.5`
- **等级**：中（乙方无责任：高）
- **修改建议**：双向对称约定，例如"任一方逾期履行的，每逾期一日按合同总价的万分之五支付违约金；累计不超过合同总价的 10%"。
- **依据**：民法典第585条（违约金）

### 5.2 B 组 · 验收

#### R05 · 验收标准不可量化 / 无验收方案
- **条款域**：验收
- **风险点**：仅写"按国家标准验收"或"双方另行确认"，验收无客观标准，争议时甲方举证困难，且可能被认定"无正当理由拒绝受领"。
- **判定线索**：
  - 定位"验收"条款
  - 触发：**无**验收附件/清单，且条款中不含以下任一量化要素：验收指标、测试方法、验收时限、通过准则、验收组织
  - 弱信号：出现"符合国家/行业标准"但未指明具体标准号（如 GB/T XXXXX）
- **等级**：高
- **修改建议**：增加附件《验收测试方案》，列明功能/性能/SLA 指标、测试环境、通过准则、验收时限（如"甲方应在收到验收申请后 10 个工作日内完成验收"），并约定逾期未提出异议视为验收通过。
- **依据**：民法典第509条、第577条（违约责任）

#### R06 · 交付物清单缺失
- **条款域**：交付 / 验收
- **风险点**：未列明交付物（软件介质、技术文档、源代码、账号权限、培训、维保手册），验收范围不清，后期"交付什么"扯皮。
- **判定线索**：
  - 检查合同是否有"交付物/交付清单/交付内容"条款或附件
  - 触发：无该条款；或条款仅写"按合同约定交付"而合同未列清单
  - 条款域覆盖检查：对"软件/系统集成/技术服务"标的，应出现 `文档 / 源代码（或托管）/ 培训 / 账号` 中至少 2 项
- **等级**：中（标的含软件/系统集成：高）
- **修改建议**：以附件形式列明交付物名称、形式、数量、交付时点、交付方式，并约定"未列入清单但为实现合同目的所必需者，乙方仍应无偿提供"。
- **依据**：行业惯例（🔧）

#### R07 · 无"逾期未提异议视为验收通过"兜底
- **条款域**：验收
- **风险点**：甲方内部流程延误导致验收迟迟不启动，乙方主张"已交付但甲方恶意拖延"，甲方反而违约。
- **判定线索**：
  - 检索关键词：`视为验收通过 / 视为验收合格 / 逾期未提出异议`
  - 触发：不存在该表述，且存在"甲方应在 X 日内完成验收"的义务
- **等级**：中
- **修改建议**：明确"甲方逾期未提出书面异议的，视为验收通过"，但同时约定"验收通过不免除乙方对隐蔽瑕疵的责任"。
- **依据**：行业惯例（🔧）

### 5.3 C 组 · 违约责任

#### R08 · 赔偿责任上限缺失或单向不对等
- **条款域**：违约责任 / 责任限制
- **风险点**：乙方责任无上限而甲方责任被限定为合同总额，或双方均无上限但乙方仅"退还已付费用"——这是最典型的显失公平条款。
- **判定线索**：
  - 检索关键词：`赔偿责任上限 / 累计赔偿 / 责任限额 / 不超过合同总价 / 直接损失`
  - 抽取双方的赔偿上限数值，做对称性比较
  - 触发：
    - `无任何责任上限约定`（双方）
    - `甲方责任上限存在` 且 `乙方责任上限不存在`
    - `乙方责任上限 < 合同总价 × 1`（低于合同额的上限对采购方极不利）
  - 特别触发：出现 `间接损失 / 可得利益 / 利润损失 / 数据丢失` 被**单向**排除
- **等级**：高
- **修改建议**：双向对称设限（如"除故意或重大过失、侵犯知识产权、违反保密义务、人身伤亡外，任一方累计赔偿责任不超过合同总价"），并明确 IP 侵权与数据泄露**不受责任上限限制**。
- **依据**：民法典第584条（可预见规则）、第577条；LegalOn "Great 8" 含责任限制 ✅

#### R09 · 违约金过低（或畸高）
- **条款域**：违约责任
- **风险点**：违约金日万分之零点几，年化低于资金成本，违约无成本；或畸高（>合同额 30%）导致可被法院调减，条款形同虚设。
- **判定线索**：
  - 抽取违约金表达式（日万分之X / 合同总价的 X% / 固定金额）
  - 折算：`日违约金率 × 365` 得年化率；`违约金累计上限 / 合同总价` 得比例
  - 触发：
    - `日违约金率 < 0.0002`（即万分之二）或 `年化 < 7.3%` → 过低
    - `累计上限 > 0.3 × 合同总价` → 可能被认定过高（民法典第585条可请求调整）
    - `无累计上限` 且 `无责任上限` → 与 R08 联动，报"无限责任"
- **等级**：中（乙方逾期无违约金：高）
- **修改建议**：日万分之五（年化 18.25%），累计上限合同总价 10–20%；超过部分不受限制的情形（如根本违约）单列。
- **依据**：**民法典第585条**：约定的违约金低于造成的损失的，法院或仲裁机构可根据当事人请求予以增加；过分高于造成的损失的，可根据请求予以适当减少 ✅

#### R10 · 履约保证金/保函缺失
- **条款域**：担保
- **风险点**：无履约担保，乙方违约后甲方只能诉讼追偿。
- **判定线索**：检索 `保证金 / 履约保函 / 银行保函 / 担保`；触发：均不存在，且合同总价 ≥ 阈值（如 100 万，由客户业务方定）
- **等级**：中
- **修改建议**：约定合同总价 5–10% 的履约保证金，或等额银行保函，有效期至质保期届满。
- **依据**：行业惯例（🔧）

### 5.4 D 组 · 知识产权

#### R11 · 定制成果知识产权归属缺失或归乙方
- **条款域**：知识产权
- **风险点**：为本项目定制开发的软件/文档/数据成果，权属未约定或约定归乙方，甲方仅获"使用权"，后续无法改造、迁移、二次开发。
- **判定线索**：
  - 检索关键词：`知识产权 / 著作权 / 专利权 / 所有权 / 归属 / 使用权 / 许可`
  - 触发：
    - 无知识产权条款（标的含软件开发/定制/内容生产）→ 高
    - 约定归乙方，或未明确归甲方 → 高
    - 甲方仅获"使用权/使用许可"，无"所有权" → 中
  - 需同时判定：是否含"可转让、可再许可、永久、不可撤销、全球"五要素
- **等级**：高
- **修改建议**：明确"本项目产生的全部知识产权（含源代码、文档、数据、衍生物）自产生之日起归甲方所有；乙方享有为本合同目的在甲方场所内的非独占使用权"，并约定乙方应交付源代码及技术文档。
- **依据**：**《民法典》第843–887条技术合同章**（技术开发合同成果归属规则）；CUAD 的 IP Clauses 分组可作分类参照 ✅

#### R12 · 知识产权侵权担保（IP Indemnity）缺失
- **条款域**：知识产权 / 赔偿
- **风险点**：第三方主张侵权时，甲方作为使用者直接成为被告，无追偿依据。
- **判定线索**：
  - 检索关键词：`第三方主张 / 侵犯第三方知识产权 / 抗辩 / 赔偿 / 承担责任`
  - 触发：无"乙方保证不侵犯第三方知识产权，若有主张由乙方负责抗辩并承担全部赔偿及甲方因此产生的费用"的约定
  - 弱信号：有保证但无"抗辩/费用承担"
- **等级**：高
- **修改建议**：加入完整 IP 侵权担保条款：乙方负责抗辩、承担全部赔偿与合理费用，并在侵权成立时自费提供替代方案或取得继续使用许可；该责任不受责任上限限制。
- **依据**：行业惯例（🔧）；LegalOn 五类失效模式①"具体条款识别"正是此类精确措辞 ✅

#### R13 · 既有 IP 与项目 IP 未区分
- **条款域**：知识产权
- **风险点**：乙方将"背景知识产权"全部保留，且定义过宽，导致甲方对核心交付物也无法主张权利。
- **判定线索**：检索 `背景知识产权 / 既有知识产权 / 乙方原有技术 / 甲方原有技术`；触发：无区分；或"背景 IP"定义中含"乙方在本项目中使用的一切技术"（过宽）
- **等级**：中
- **修改建议**：明确区分"背景知识产权"（各自原有）与"项目成果"（归甲方），并附背景 IP 清单作为附件；乙方授予甲方对背景 IP 的永久、免费、可转授的实施许可。
- **依据**：行业惯例（🔧）

### 5.5 E 组 · 数据与保密

#### R14 · 个人信息委托处理条款不合规
- **条款域**：数据合规
- **风险点**：合同涉及用户信息/员工信息/通信相关信息，但未签署《个人信息委托处理协议》，甲方作为个人信息处理者将直接承担合规责任。
- **判定线索**：
  - 触发场景识别：标的含 `运维 / 客服 / 数据分析 / 系统开发 / 营销`，且合同出现 `用户信息 / 个人信息 / 手机号 / 客户资料`
  - 六要素检查（缺一即报）：**① 处理目的 ② 处理期限 ③ 处理方式 ④ 个人信息种类 ⑤ 保护措施 ⑥ 双方权利义务**
  - 触发：**存在个人信息处理场景** 且 六要素任一缺失 → 高危
- **等级**：高
- **修改建议**：签署标准《个人信息委托处理协议》作为附件，明确六要素 + 受托人不得转委托 + 帮助甲方履行个人信息权利响应义务 + 合同终止后返还或删除 + 违规的赔偿责任（不受责任上限限制）。
- **依据**：**《个人信息保护法》第21条**（委托处理须约定目的、期限、处理方式、信息种类、保护措施、双方权利义务，并监督受托方）

#### R15 · 数据出境/境外远程访问未约定
- **条款域**：数据合规
- **风险点**：境外主体或跨境运维导致数据出境，未经安全评估即构成违规。
- **判定线索**：
  - 检索关键词：`境外 / 出境 / 跨境 / 海外 / 远程访问 / 境外服务器`
  - 主体检查：乙方或其分包方是否为境外主体，是否约定境外运维/境外存储
  - 触发：存在跨境因素且**无**"数据不出境"或"未经甲方书面同意并通过法定程序不得出境"的约定
- **等级**：高
- **修改建议**：约定"未经甲方书面同意，乙方不得将数据（含备份、日志）传输至境外或允许境外主体访问；确需出境的，应经甲方书面同意并由甲方完成法定出境程序"。
- **依据**：《数据安全法》第21条（数据分类分级）、第36条；《个人信息保护法》第38–40条（跨境提供）

#### R16 · 数据安全事件通知义务与时限缺失
- **条款域**：数据合规 / 安全
- **风险点**：发生泄露后通知延迟，甲方错过监管报告窗口，处罚加重。
- **判定线索**：
  - 检索关键词：`数据泄露 / 安全事件 / 网络安全事件 / 通知 / 小时 / 立即`
  - 抽取通知时限数值（小时/日）
  - 触发：无通知义务；或时限 > 24 小时；或无"协助调查、配合报告监管"义务
- **等级**：高（含大量个人信息：绝对高）
- **修改建议**："乙方发现或应当发现数据安全事件后 2 小时内以电话+书面方式通知甲方，24 小时内提交书面报告，配合甲方履行监管报告与用户告知义务，并承担由此产生的全部损失。"
- **依据**：《网络安全法》第42条；《个人信息保护法》第57条

#### R17 · 保密信息范围与期限不足
- **条款域**：保密
- **风险点**：保密范围未含口头披露、期限过短或单向保密，甲方信息披露后无保护。
- **判定线索**：
  - 单向检查：**只约束甲方**不约束乙方 → 高
  - 范围检查：是否含"口头、视觉、电子形式披露的信息"
  - 期限检查：抽取保密期限数值；`< 合同终止后 3 年` → 中
  - 例外检查：是否含法定披露例外（法律要求、已公开、已独立开发）——**缺失例外条款对乙方过严，反而可能整条被判不适用**
- **等级**：中（单向保密：高）
- **修改建议**：双向对等；范围含口头/电子；期限"合同终止后 5 年（商业秘密长期有效）"；加入四项法定例外；明确违约的赔偿与禁令救济。
- **依据**：反不正当竞争法第9条；ContractNLI 的 NDA 假设体系可作建模参照 ✅

### 5.6 F 组 · SLA / 服务质量

#### R18 · SLA 指标不可量化或无罚则
- **条款域**：SLA
- **风险点**：仅有"保证系统稳定运行""及时响应"等表述，无可用率、响应时长、恢复时长等量化指标，也无未达标的服务抵扣/罚则，SLA 形同虚设。
- **判定线索**：
  - 检索关键词：`服务水平 / SLA / 可用率 / 可用性 / 响应时间 / 故障恢复 / MTTR / 服务等级`
  - 触发：
    - 无 SLA 条款（标的含运维/云/网络服务）→ 高
    - 有 SLA 但**无量化数值**（% / 小时 / 分钟）→ 高
    - 有量化指标但**无未达标后果**（服务抵扣/罚款/解除权）→ 高
  - 数值合理性：可用率承诺 < 99.5% → 中；无赔付计算基数（按服务费？按合同额？）→ 中
- **等级**：高
- **修改建议**：附件《服务水平协议》列出：可用率（如 99.9%，按月统计）、P1/P2 故障响应与恢复时限、未达标按当期服务费的 X% 逐档抵扣、连续 2 个季度未达标甲方可无责解除并索赔。
- **依据**：LegalOn 失效模式②"数值阈值检查" ✅；行业惯例（🔧）

#### R19 · SLA 罚则上限过低 / 与解除权脱钩
- **条款域**：SLA
- **风险点**：罚则上限仅当月服务费的 5%，且不构成解除事由，SLA 无实际约束力。
- **判定线索**：抽取 SLA 罚则上限比例与计算基数；触发：`上限 < 当期服务费 × 10%` 或 `罚则与解除权无关联`
- **等级**：中
- **修改建议**：罚则上限 ≥ 当期服务费 30%（或合同年度金额 10%）；并约定"任一年度累计 3 次未达标，甲方可解除合同并要求赔偿"。
- **依据**：行业惯例（🔧）

### 5.7 G 组 · 终止

#### R20 · 甲方便利解除权缺失
- **条款域**：终止
- **风险点**：无"甲方提前通知无偿/低偿解除"权利，业务调整或供应商替换时被锁定；或解除条件仅限"乙方重大违约"且定义极窄。
- **判定线索**：
  - 检索关键词：`解除 / 终止 / 提前终止 / 单方解除 / 无因解除`
  - 触发：
    - 无甲方单方解除权 → 高
    - 甲方解除权需"乙方根本违约且经催告 30 日仍未改正"且无其他情形 → 中
    - 缺少以下任一即时解除情形 → 中：`资质失效 / 被列入失信名单 / 被吊销许可证 / 重大安全事故 / 转包`
  - 反向检查：乙方是否有单方解除权（若有且条件宽于甲方 → 高）
- **等级**：高
- **修改建议**：约定"甲方可提前 30 日书面通知后无责解除，按已完成工作量结算"；并单列甲方可立即解除的情形（乙方资质失效、被列入失信被执行人名单、发生重大安全或数据事件、未经同意转包）。
- **依据**：《民法典》第562条（约定解除）、第563条（法定解除）

#### R21 · 解除后果与过渡安排缺失
- **条款域**：终止
- **风险点**：解除后数据/源代码/账号不交回，业务中断；已付款项不返还。
- **判定线索**：
  - 是否存在"合同终止后 X 日内"的义务清单
  - 四要素检查（缺一即报）：**① 数据与资料移交/删除 ② 源代码或技术文档交付 ③ 过渡期服务（如 90 天） ④ 已付款项的处理（按比例返还/不返还）**
- **等级**：中
- **修改建议**：约定解除后乙方 10 个工作日内完成数据导出与移交、按甲方要求删除副本并出具删除证明、提供不少于 90 日的过渡服务；已支付但未履行部分的款项应返还。
- **依据**：LegalOn "Great 8" 含"终止后果" ✅；《个人信息保护法》第21条（委托终止后返还或删除）

### 5.8 H 组 · 转让与分包

#### R22 · 转让/分包单向限制
- **条款域**：转让 / 分包
- **风险点**：约定"甲方可自由转让、乙方不得转让"，形式对等但忽略：乙方**分包**未限制，实际由无资质第三方履约。
- **判定线索**：
  - 分别检查"转让（让与）"与"分包/转包"两部分
  - 触发：
    - 无分包限制条款 → 高（标的含施工/运维/集成）
    - 允许分包但**无**"分包不解除乙方责任 + 分包方须经甲方书面同意 + 分包方须具备相应资质"三要素 → 中
    - 约定"未经甲方同意不得转让"但同时约定"乙方可将本合同项下收款权转让给金融机构"且未通知甲方 → 中
- **等级**：中（电信业务/涉密/涉数据场景：高）
- **修改建议**：约定"未经甲方书面同意，乙方不得将本合同全部或部分权利义务转让、分包或转包；经同意的分包不解除乙方责任，分包方应具备履约资质并签署背靠背的保密与数据条款"。
- **依据**：**《民法典》第545条**（债权转让）、第551条（债务转移需债权人同意）；《电信条例》对转包的限制（属地法规需复核）

### 5.9 I 组 · 争议解决

#### R23 · 管辖法院对甲方不利 / 适用法律为境外法
- **条款域**：争议解决
- **风险点**：约定乙方所在地法院、境外仲裁机构或外国法为准据法，甲方维权成本剧增，且可能丧失主场优势。
- **判定线索**：
  - 抽取"管辖法院/仲裁机构"名称，与甲方所在地（浙江/杭州）比对
  - 触发：
    - 乙方所在地法院 / 境外法院 / 境外仲裁机构（如 HKIAC、SIAC、ICC）→ 高
    - 仲裁机构名称不存在、名称不唯一、或同时约定"诉讼或仲裁" → 中（条款可能无效）
    - 准据法非中国法 → 高
  - 缺失判定：无争议解决条款 → 中（适用法定管辖，未必不利，但应明确）
- **等级**：高（境外仲裁/境外法：绝对高）；中（非最优但对甲方非致命的约定）
- **修改建议**："因本合同引起的争议，双方应友好协商；协商不成的，任何一方可向甲方所在地（杭州市××区）有管辖权的人民法院提起诉讼。本合同适用中华人民共和国法律（不含港澳台地区法律）。"
- **依据**：《民事诉讼法》第35条（协议管辖）；《民法典》第467条

### 5.10 J 组 · 不可抗力

#### R24 · 不可抗力定义过宽 / 后果不明
- **条款域**：不可抗力
- **风险点**：将"供应商停产""上游涨价""资金困难""员工罢工"纳入不可抗力，乙方可据此免责；或未约定通知时限、证明义务、超期解除权。
- **判定线索**：
  - 抽取不可抗力定义中的列举项
  - 触发：
    - 列举中含 `涨价 / 成本上升 / 停产 / 资金 / 员工流失 / 原材料短缺 / 供应链中断` 等经营风险 → 高
    - 缺少以下任一要素 → 中：**① 通知时限（如 5 日内书面通知）② 证明文件 ③ 减损义务 ④ 持续超过 X 日任一方可解除**
    - 约定"金钱给付义务可因不可抗力免除" → 中
- **等级**：中（含经营风险列举：高）
- **修改建议**：参照《民法典》第180条定义（不能预见、不能避免且不能克服的客观情况），列举典型情形（自然灾害、战争、政府行为、大规模疫情），并明确：5 日内书面通知 + 提供证明 + 减损义务 + 持续超过 60 日任一方可解除 + **金钱给付义务不得因不可抗力免除**。
- **依据**：**《民法典》第590条**（不可抗力免责及通知证明义务）✅

### 5.11 K 组 · 审计权

#### R25 · 审计/稽核权缺失
- **条款域**：审计权
- **风险点**：无法核查乙方计费、分包、数据处理的合规性，尤其转售/代维/按量计费类合同。
- **判定线索**：
  - 检索关键词：`审计 / 稽核 / 查验 / 检查 / 查阅 / 账目 / 记录 / 系统日志`
  - 触发：
    - 完全无审计权条款 → 中（按量计费/代维类：高）
    - 有审计权但缺以下要素 → 中：**① 甲方或甲方委托的第三方 ② 提前 X 日通知 ③ 每年 X 次 ④ 乙方配合义务 ⑤ 发现差异的处理**
- **等级**：中（按量计费/代维/数据处理类：高）
- **修改建议**："甲方及其委托的第三方有权在提前 10 个工作日通知后，每年不超过 2 次对乙方与本合同履行相关的账目、记录、系统日志进行审计；乙方应予配合。审计发现乙方多收费用的，乙方应退还并支付差额 20% 的违约金，审计费用由乙方承担。"
- **依据**：CUAD 41 类标签含 "Audit Rights" ✅；行业惯例（🔧）

### 5.12 L 组 · 电信/国企特有条目

#### R26 · 资质与许可承诺缺失
- **条款域**：主体资质
- **风险点**：履约需电信业务经营许可、等保测评、进网许可、涉密资质等，合同未要求，导致实际无资质履约、行政处罚连带。
- **判定线索**：
  - 按标的类型映射所需资质（如增值电信业务 → 增值电信业务经营许可证；网络设备 → 进网许可证/3C；涉密 → 涉密信息系统集成资质）
  - 触发：所需资质未在合同中作为乙方陈述与保证；或无"资质失效即为根本违约、甲方可立即解除"的约定
- **等级**：高
- **修改建议**：加入乙方陈述保证"具备履行本合同所需的全部资质、许可与授权，并在合同期内持续有效"；约定资质失效或虚假陈述时甲方可立即解除、要求返还已付款项并赔偿损失。
- **依据**：《电信条例》（具体条款需按最新版本复核）；《网络安全法》第21条（等级保护）

#### R27 · 廉洁与反商业贿赂条款缺失
- **条款域**：合规（国企刚需）
- **风险点**：运营商/国企采购合规要求，缺失则审计不过。
- **判定线索**：检索 `廉洁 / 反商业贿赂 / 反腐败 / 利益冲突 / 举报`；触发：均不存在
- **等级**：中
- **修改建议**：加入廉洁条款：乙方不得向甲方员工及其近亲属提供任何形式利益；违反的，甲方可解除合同、要求合同总价 20% 的违约金、列入不良供应商名单；乙方应配合甲方合规调查。
- **依据**：国务院国资委/运营商集团采购合规要求（需客户提供具体制度文号）

> **落地提示**：以上 27 条中，**R01–R14 共 14 条可完全由确定性检查器实现**（正则/数值/存在性/求和），交付周期短、准确率高、演示效果稳定——**建议作为 demo 首发的核心 14 条**。R15–R27 为语义判断或半结构化判断，作为第二批。

## 8. 待确认问题（需客户/Lead 拍板）

1. **"核心风险召回≥88%"的分母是什么？**（D1/D2/D3/D4，见 §3.1）—— 不定这个，无法验收。
2. **"核心风险"是哪几条？** 从 27 条里选 10–15 条 P0，需客户法务书面确认后锁定。
3. **评测集由谁提供、多少份、是否脱敏、能否双人标注？** 建议 ≥30 份，双人+仲裁。
4. **"10 秒"的口径**：T1 首屏 / T2 完整报告？扫描件是否在内？
5. **数据不出网是硬约束吗？** 决定用 API 还是本地部署，直接影响可行性边界（§1.7）。
6. **是否要求生成式 AI 服务备案/算法备案？** 法大大已备案，运营商采购可能作为硬性资质项。
7. **是否需要 docx 修订模式回写？** 影响工作量（P1 级）。
8. **"审查立场"是否需要甲乙双方切换？** 通义法睿与法大大都把 position 作为参数，建议 demo 阶段先只做甲方。
9. **是否要对标某个具体竞品？** 若对标 LegalOn/法大大，需按 §3.4 的口径重做对比，不能直接引用其自测数字。

1. **"我们不比模型谁更聪明，我们比谁的规则清单更可维护、每条规定性检查更可审计。"**（依据 §1.3 harness 架构）
