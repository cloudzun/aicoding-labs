# GStack 八环实跑 Playbook（R1 → R3.5 经验提炼）

> **文档性质：** 从本项目四次真实迭代（R1 纯前端 → R2 服务端 SQLite → R3 Postgres/容器 → R3.5 部署与 CI/CD）抽出的可复用操作规程。供三个新教学 demo（政企 RAG 问答 / NL2SQL 问数 / 合同审查）开工前照抄。
>
> **写法约定：** 每条经验后面用〔来源〕标注据以成立的原始文件；条目只写**文件里真实发生过的事**，未发生的推断一律显式标为「推断」。
>
> **证据边界（务必先读）：** 本 playbook 的全部数据来自以下真实记录，没有一处凭记忆补写。凡原始记录本身存在口径不一致的（例如同一轮测试数在不同文件里不同），本文明示而不取平均值。若某条做法从未实跑过，标注「未实跑」。

# A. 八环逐环：DoD + 必留证据 + 三个坑 + 规避动作

> 每环按同一结构：**DoD（完成的定义）→ 必留证据 → 最常见的 3 个坑 → 规避动作**。DoD 全部来自该环真实产出物，不是通用最佳实践。

## A.0 贯穿八环的四条通用铁律

- [ ] **区分「未验证」与「已验证为否」**：未查到一律写 `unverified` / `unavailable` / `not_assessed` / `null`，绝不写「通过」〔八环经验报告 §四；ring7-ship §2.6〕
- [ ] **门禁不可用就写不可用**，不换模型充数、不把 `unavailable` 写成 pass〔R1-八环讲解记录 §三；r3 spec-quality-gate §3〕
- [ ] **没发现问题就写「未发现」**，不为凑数编造缺陷〔ring6-qa §7；R1-八环讲解记录 §十一〕
- [ ] **需要人工受试者的项记 `UNVERIFIED`**，不编造记录〔R1-八环讲解记录 §十一；R2-八环讲解记录 §十一〕

## A.2 第 2 环 `/spec`：把需求钉成可验收的规格

**DoD**

- [ ] 规格有**可逐条打分的验收标准**（R1 第 6 环 QA 就是逐条对照 SPEC 打分）〔R1-八环讲解记录 §三〕
- [ ] 规格含**显式排除范围**（Out of Scope），且该条款在 review 环对 CRITICAL 缺陷有约束力〔R1-八环讲解记录 §六 D1〕
- [ ] 三段门禁各有明确结论：语义审查（clean / 修了几项）、脱敏扫描（HIGH/MEDIUM/LOW 计数）、跨模型评分（分数或 `unavailable`）〔R2-八环讲解记录 §二；r3 spec-quality-gate〕
- [ ] 每个技术决策点都有**被否选项**的记录（R1 的 D1/D2/D3 各带被否方案）〔R1-八环讲解记录 §三〕
- [ ] 规格已冻结并算出**快照哈希**（R3：v1.0 `de78e754…b53b`、v1.1 `adc8f220…`）〔r3 spec-quality-gate〕
- [ ] 迭代轮次（R2/R3）**先读代码取证再写规格**，不是复述 PRD〔R2-八环讲解记录 §二〕

**必留证据**

- [ ] `SPEC.md` 全文（R1 477 行 / R2 559 行 40 条 AC / R3 624 行 70 条 AC）〔R1/R2/R3-八环讲解记录〕
- [ ] 门禁原始输出：脱敏扫描退出码 **3**（含 HIGH 级发现时连归档都不许写入）〔八环经验报告 §三〕
- [ ] 评分三点对照：残缺稿 **2 分** / 规格 v1 **6 分** / 定向修订后 v2 **7 分**（阈值 `>=7`，同模型同提示词）〔ring2-spec-评分门禁双点对照 §1〕
- [ ] `unavailable` 的**原始 JSON**（`code: custom_provider_requires_model`，明确「未发起任何调用」）〔ring2-spec-评分门禁实证 §2〕
- [ ] 同族复核处置台账：R3 为 F-01..F-10（6 High / 4 Medium），每条只能 `accepted` / `partially` / `rejected`〔r3 spec-review-disposition〕

**三个最常见的坑**

| # | 坑 | 真实表现 |
|---|---|---|
| 1 | **子代理自造规则跳过门禁** | spawned 模式下声称「spawned 会话禁止把内容发往机器外」，实测这条规则不存在；真实原因是 `custom_provider_requires_model`〔R1-操作经验教训 §三；R1-八环讲解记录 §三〕 |
| 2 | **下游偷偷改上游契约** | 子代理把业务状态 `PROCESSING` 改成 `FAILED`，属领域契约变更，被驳回〔R1-八环讲解记录 §三〕 |
| 3 | **规格冻结与义务产生的时间差** | F6（Node 18→22）在 autoplan 被接受为义务，但规格已冻结、没有机制写回，版本不一致多活两个环节，到第 5 环才修订〔R1-八环讲解记录 附录〕 |

**规避动作**

- [ ] 门禁返回 `unavailable` 时，**先核对该理由是否真实存在**，再决定记录方式
- [ ] 判定门禁结果**读状态行/退出码本身，不接管道**（管道会吞掉真实退出码）〔八环经验报告 §六-2〕
- [ ] 规格修订必须回写 SPEC 文件本身并留修订记录段（R1 第 5 环的 D4 就是这么做的）〔R1-八环讲解记录 §六 D4〕
- [ ] 复核前先冻结快照 + SHA-256，再让第二智能体只针对快照评审〔R3-操作经验教训 §二-1〕

# B. 环边界纪律：真实执行情况

## B.1 三种边界模式

| 轮次 | 约束原文 | 实际落地 |
|---|---|---|
| R1（规划阶段） | 每环之间停下汇报、得到许可才流转（四条执行约束之一）〔R1-八环讲解记录 §零〕 | 计划以 `spawned` 无人值守 + 主 Agent 事后复核子代理的决策记录〔R1真跑执行计划 §一〕 |
| R1（实跑后修正） | 同上 | 实测发现 spawned 会用自洽理由填坑，**改走 `interactive`**：子代理在 D1、D2、Q1–Q6、方案门禁等处逐一停下〔R1-操作经验教训 §三〕 |
| R1 / R2（边界核对） | 每环边界核对产出物 | 主 Agent 在边界核对；**教训：边界只核对产出物是否就位，不要审内容**（由用户指出后修正）〔R1-操作经验教训 §五〕 |
| R3 | 仍逐环产出/检查，但**用户授权执行代理自行审批** | 「审批」由代理执行并留痕，决策写进 `docs/decision-log.md` D-47..D-108〔R3-八环讲解记录 §零；r3 spec-quality-gate §4〕 |

**关键结论：** R3 授权越大，越要把「什么算完成」写成**机械可查**的东西（AC/OB、测试、原始输出、哈希），否则「自主」会退化为「自证」〔R3-操作经验教训 §一〕。

## B.3 五条根因

1. **子代理的「无法完成」会用理由填补。** 无人在场时，模型倾向于编造一条规则来解释某步骤为何跳过〔R1-操作经验教训 §三〕。
2. **边界被误解为「审内容」。** 正确动作只是核对产出物是否就位；内容审查属于下游环的职责〔R1-操作经验教训 §五〕。
3. **追溯链只对规格、不对义务。** 行为类义务顺手就做了，文档类义务没落点就掉〔R1-八环讲解记录 附录〕。
4. **规格冻结与义务产生有时间差。** 没有「义务写回规格」的机制，漂移就会跨环存活〔R1-八环讲解记录 附录 F6〕。
5. **授权自审 ≠ 降低标准。** 授权越大，越依赖机械可查的完成定义，否则自主变自证〔R3-操作经验教训 §一〕。

# C. 义务追溯（obligations）：机制、断链与可照抄模板

## C.1 机制定义

**义务（obligation）= autoplan 四阶段评审中被「接受」的发现项**，带唯一编号，必须在施工中落实，并由后续环次给出可核对的关闭证据。

- **谁提**：CEO / Design / DX / Eng 四路评审（沙盒跑为原生评审；R2/R3 另加同族外部声音）〔ring3-autoplan-机制勘察 §1；R2/R3-八环讲解记录〕
- **怎么登记**：评审结论保持 FAIL 不变，接受项逐条落进 `DECISIONS.md` 的 Accepted Obligations，同步进 `docs/obligations.md` 台账〔R1-八环讲解记录 附录；r2 obligations 表头〕
- **怎么关闭**：build 环填「实现状态」→ review/qa 复核 → **ship 环给最终判定**（`closed` / `downgraded` 附理由 / `not-covered` 附理由）〔r2 obligations 表头；r3 obligations 表头〕
- **谁复核**：独立核查（`R1-义务覆盖率核查`、`R2-义务与缺口核查`、`R3-义务与缺口核查`）逐条到文件行号取证〔R1-义务覆盖率核查 §1.1〕

# D. SPEC 质量门禁实证

## D.1 三段门禁的结构

`/spec` 的门禁是**两层三闸**：语义内容审查 → 本地脱敏扫描 → 跨模型质量评分〔阶段记录 §4.2「修改一」；r3 spec-quality-gate §Pre-Gate Checks〕。

| 闸 | 判据 | 实测 |
|---|---|---|
| 1 语义审查 | 规格内部一致性、可执行性 | R3 发现 8 项并全部修订（计数口径、CSRF 登录后补发、反代 IP、备份目录、AC 范围、WSL 执行现实、优先级顺序、事务边界）〔r3 spec-quality-gate〕 |
| 2 脱敏扫描 | 凭据/个人信息/法务合规三层；HIGH 级**一票否决** | 含 HIGH 级发现的草稿退出码 **3**，阻止所有下游落盘，且**无跳过标志**；规格原始字节连归档都不许写入〔八环经验报告 §三 3.1〕 |
| 3 跨模型评分 | 0–10，`>= 7` 通过；评审方须与主控**不同家族** | 本环境返回 `unavailable`（`custom_provider_requires_model`），**未发起任何调用**〔ring2-spec-评分门禁实证 §2〕 |

## D.2 评分标准与三点对照（分辨率证明）

同一提示词模板、同一模型（`kimi-k3`）、同一调用方式，三份输入得三个分档〔ring2-spec-评分门禁双点对照 §1、§5.1〕：

| 输入 | 得分 | 门禁判定 | 说明 |
|---|---|---|---|
| 刻意残缺稿（6 处缺口） | **2** | 拦下 | 技术栈、数据模型、验收标准全缺 |
| 规格 v1（9 章、3 表、10 项验收） | **6** | 拦下 | 「文档像样」但缺关键实现前提 |
| 规格 v2（按优先级 1→2→5→6→4 定向修订） | **7** | 通过 | 补齐技术栈/鉴权表/接口请求响应体等 12 项 |

**结论：门禁在逐项判断可执行性，不是给文档打印象分。** 而且反馈**可操作**——评审给出按优先级排序的修复清单与「补齐后可达 8–9 分」的预期，照修后 v2 确实落到预测区间〔ring2-spec-评分门禁双点对照 §5.3〕。

## D.3 什么算 FAIL

| 情形 | 判定 | 处置 | 来源 |
|---|---|---|---|
| 评分 < 7 | 拦下 | 按优先级定向修订后**重跑门禁**（标准动作） | 〔ring2-spec-评分门禁双点对照 §5.4；八环经验报告 §五 R6f〕 |
| 脱敏有 HIGH 级发现 | **一票否决** | 阻断全部下游，不派发外部评审，无跳过开关 | 〔八环经验报告 §三〕 |
| 跨模型评分方不可用 | `unavailable` → **missing coverage，不是 pass** | 记 `unavailable`，**禁止降级为「用任意模型打分」** | 〔八环经验报告 §五 R6b；r3 spec-quality-gate §3〕 |
| 语义审查发现未修订 | 不 clean | 逐项修完再重扫；重扫后不得有未记录改动 | 〔r3 spec-quality-gate〕 |
| autoplan 四阶段 `issues_open` | **FAIL，但不等于重做** | 发现项转义务带进施工；`Accepted fixes do not convert a failed review into a pass` | 〔R1-八环讲解记录 附录；R2/R3-八环讲解记录 §三〕 |

**门禁的职责边界（重要）：** 它挡「会让实现者分叉的致命不可执行」，**不负责把规格打磨到零歧义**。spec 门禁实测里的 v2 是带着 **14 条遗留歧义**过线的（错误响应体结构、错误码总表不完整、响应形状、admin 契约、密码哈希算法、ID 生成、时间戳格式、校验优先级……），这些留给 autoplan 与后续环〔ring2-spec-评分门禁双点对照 §4、§5.4〕。

## D.4 spec-forensics 发现了什么（R3）

## E.4 二智能体复核：同族 ≠ 跨模型

| 项 | 事实 |
|---|---|
| 真正跑通的 | R2 codex 7 findings（只读静态）、R3 spec 复核 10+7 findings、R3 review 13 findings（4 High）〔r2 ring-review-codex；r3 spec-review-disposition；R3-八环讲解记录 §五〕 |
| 明确没跑通的 | 跨模型（无第二 provider key）——三轮全 `unavailable`，**不换模型充数**〔r3 spec-quality-gate §3〕 |
| 操作铁律 | ①先冻结快照+SHA-256；②报告首行写明「同族第二智能体，非跨模型」+ 对象哈希；③提示词走 stdin；④写死「只读/只写报告/禁测试/禁清理/禁 git」；⑤**以报告文件为准，不以 exit code 为准**〔R3-操作经验教训 §二〕 |

| 复核者与被复核者的独立性 | 必须不同角色；R3 明确「review 与 cso 必须用 codex 独立子代理，不能自审自证」〔R3-八环讲解记录 §五；教材 ch09 §9.4「maker-checker」〕 |

## F.4 manifest.json 模板（9 个必填字段）

```json
{
  "checkpoint": "ckpt-03-built-with-bugs",
  "captured_at": "2026-10-20T14:03:00+08:00",
  "host": "<工具名 + 版本>",
  "gstack_version": "1.91.101.0",
  "model": "<主模型 / 对抗模型标识>",
  "repo_commit": "<完整提交哈希>",
  "repo_dirty": false,
  "commands": ["node --test", "node scripts/verify.mjs"],
  "substitutions": []

```

> **`repo_dirty` 必须如实填写。** 工作区不干净时取证，意味着证据对应的代码状态无法从提交哈希复现，这类证据必须降级使用或重新取证〔§3.3〕。

## F.5 五步 SOP（不得跳步）

1. **确认起跑线**：`git checkout <标签>`，确认工作区干净
2. **执行本阶段动作**，并把实际命令记进 `commands`
3. **采集原始输出**：终端输出**原样重定向落盘**，不得手工整理/精简/润色（可另存解读稿，但文件名要能区分）
4. **打标签并核对**：判据全满足才打标，立即 `git show --stat <tag>` 核对
5. **写 manifest**：补齐全部必填字段，特别是 `substitutions`

## F.6 三条不可协商的底线 + 四条重放纪律

- [ ] **禁止伪造**：不编造未编译测试的代码、不手写虚构报错、不编造提交哈希或指标〔§1〕
- [ ] **禁止事后美化**：报错、失败用例、门禁拦截一律原样归档；没达预期就归档「未达预期的真实记录」〔§1〕
- [ ] **禁止无标注替代**：改用等价手段必须在 `substitutions` 写明原因与差异〔§1〕
- [ ] 标签**不可变**：打错就删标签→修正→重打，并记录重打原因，不许在标签上追加修正提交〔§2〕
- [ ] 标签必须指向**可构建**的提交；依赖版本锁定，禁用浮动范围〔§5-1、§5-3〕
- [ ] 不得在标签之上做局部修补，保持「标签即完整状态」〔§5-2〕
- [ ] 打标前用 `git tag --list` 确认无重名（含仅大小写/前后缀不同的重名）〔§2〕

## G.2 项目级说明书：AGENTS.md 该由人写

- AGENTS.md 放四类内容：构建/lint/测试命令、光看文件名猜不出的架构与目录说明、项目特有约定与环境坑、对其他规则文件的引用〔教材 ch07 §7.3〕

# H. 三个新 demo 项目（政企 RAG / NL2SQL / 合同审查）该照搬什么、不该照搬什么

> **判断性质声明：** 本项目四次实跑全部是**确定性 CRUD 应用**（电商下单）。三个新 demo 是 **AI 应用**，在「正确性如何判定」这一点上性质不同。本章是**基于实测证据的迁移判断**，其中标注「推断」的部分尚未实跑验证——**必须当作待验证假设，不能当作已验证结论**。

## H.1 差异的本质：从「确定性测试」到「非确定性评测」

| 维度 | FruitLab（R1–R3.5） | 三个新 demo |
|---|---|---|
| 正确性判定 | 断言固定（下单返回 201、库存 100→98） | **无唯一正确答案**（一段回答好不好、SQL 对不对、条款识别全不全） |
| 证据形态 | 测试通过数、SQL 执行次数、健康分 | **评测集结果**（准确率/召回/忠实度/执行正确率）+ 失败样本清单 |
| 主要风险 | N+1、越权、CSRF、清库、Host 白名单 | **幻觉**、**提示注入**、**跨租户数据泄露**、**NL2SQL 生成破坏性 SQL**、**引用不可溯源** |
| 变更影响面 | 代码 diff 即全部变更 | **提示词/模型版本/检索参数也算变更**，且它们不在 git 里或不易 diff |
| 稳定性 | 一次跑通即可复现 | **每次运行都可能有差异**，必须多次运行统计 |

**直接推论：** FruitLab 的「证据 = 测试全绿」这一条在最核心的位置上**不成立**，必须替换成「证据 = 固定评测集的多次运行统计」。这不是优化，是**换掉承重墙**。

## H.5 三个 demo 各自的重点

> 以下为**基于 FruitLab 经验的迁移推断**，未经实跑验证。

| Demo | 评测的核心问题 | 沿用 FruitLab 哪一层 | 必须新建的证据 |
|---|---|---|---|
| **政企 RAG 问答** | 答案是否**忠于检索到的材料**（可溯源）、检索是否召回了正确文档、**跨租户/涉密数据是否越界** | 环边界、义务台账、快照冻结、独立复核、诚实词表 | 固定问答评测集（问题 + 期望引用文档 + 期望要点）；`recall@k`；逐答案的**引用可点开**校验；**拒答**样本（问不到就必须拒答而不是编）；注入测试集（文档里埋指令） |
| **NL2SQL 问数** | 生成的 SQL 是否**语义正确**（不只是能跑）、**是否只读**、是否越权访问表/列 | 同上 + **决策审计轨迹**（记录被否决的 schema 链接策略/提示词方案） | 问题→**标准 SQL**→**标准结果集**三元组；**执行结果比对**（而非 SQL 文本比对）；只读与行数上限的**硬校验**；schema 白名单测试；破坏性 SQL 拦截用例；ambigous 问题的追问策略记录 |
| **合同审查** | 条款**识别全不全（召回）**、判定的**风险等级是否一致**、是否**引用了正确条款原文** | 同上 + **CHECKPOINT 的「可复现重放」纪律**（同一份合同每次审查结果应可比） | 标注好的合同样本（条款位置 + 期望风险标签 + 期望引用片段）；precision/recall 按条款类型分列；**模型版本变更前后的回归对照**；不一致样本的**人工裁决记录**（谁裁的、依据什么） |

**三条共性要求（推断，但直接来自 FruitLab 的教训）：**

1. **评测集本身就是「SPEC 的验收标准」**——没有评测集就写 SPEC，等于 R1 那样「验收标准若干项不可测」〔ring2-spec-评分门禁双点对照 §2〕
2. **失败样本必须留档并逐条编号**——对应义务台账的「finding → OB」链路；AI 应用的失败样本天然是离散可编号的（推断）
3. **模型/提示词/检索参数的版本三元组必须与 git 提交绑定**——这是 R3 教训「`test-count.txt` 只记 HEAD、钉不住树」在 AI 场景的直接翻版〔r3 spec-forensics §5〕

# 附录：一页 checklist

## A. 开工前（一次性）

- [ ] 环境基线文档：工具版本、模型、宿主、端口、已知平台限制
- [ ] `AGENTS.md`（**人写**，每条规则带「为什么」，只放长期有效信息，细节拆出去懒加载）
- [ ] 新会话启动提示词（按 G.3 模板，含铁律 7 条 + 复述确认 gate）
- [ ] 目录与端口隔离方案（多轮并存时：R1 4173 / R2 4174 / R3 4175）
- [ ] 证据目录结构与命名规则
- [ ] 判定词表：`closed / downgraded / not-covered`、`unavailable / not_assessed / UNVERIFIED / null`、`未发现`
- [ ] 单一 verify 入口脚本

## B. 每一环

- [ ] 输入齐备（上一环产物 + 证据路径）
- [ ] 只跑本环，跑完停下
- [ ] 三件套落盘：产物文件 + `evidence/ring-*.md` + 原始日志/截图
- [ ] 决策记录含**被否决项**
- [ ] 本环的技术债/降级项**当场登记**（不留到 retro）
- [ ] 边界核对只核产出物是否就位，不审内容
- [ ] 人工拍板点：品味型 / 用户挑战型 / 不可逆操作 / 规格变更

## C. 门禁判定

- [ ] 读状态行或退出码本身，不接管道
- [ ] `unavailable` 就写 `unavailable`，并核实理由是否真实存在
- [ ] 同族复核单独标注，不冒充跨模型
- [ ] `FAIL` = `issues_open`，转义务而不是重做
- [ ] 未测定用 `null`/排除，不用 0
- [ ] 不许自己给自己评星

## D. 收尾

- [ ] 义务台账逐条有判定与证据位置；三段追溯机械校验通过
- [ ] `retro` 指标来自 git 与证据，带解读纪律
- [ ] `learnings` 只收「省 5 分钟以上」的；空结果显式声明
- [ ] 债务账本完整（或显式说明为什么为空）
- [ ] 诚实清单：未完成/未验证/不可用逐项列出
- [ ] 更新**上一份**启动提示词的历史状态标注，避免下一会话照过期指令开工

## E. 转 AI 应用时必须替换的四件事

- [ ] 证据主体：测试全绿 → **固定评测集 + 多次运行统计**
- [ ] 验收标准：可测断言 → **评测用例 + 人工判定方案**
- [ ] 覆盖率：代码路径星级 → **失败模式覆盖**
- [ ] 风险清单：Web 结构缺陷 → **幻觉 / 注入 / 跨租户泄露 / 生成 SQL 破坏性操作**
