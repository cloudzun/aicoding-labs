# 三案例整体回顾与 FDE 场景 GStack 最佳实践

> **来源纪律：** 本文所有数字均出自三个项目的 `qa-report.md` 与 `evidence/`，不引入任何未实测数据；未验证的写"未验证"。
> **定位：** 课程从"工具层（R1–R3.5）"升到"方法层"的总结章。三个案例不是三次炫技，是三次**同一套方法在不同约束下的压力测试**。

---

## 一、三个案例做了什么

| | ① 政企 RAG 问答 | ② NL2SQL 问数 | ③ 合同审查 |
|---|---|---|---|
| 一句话 | 答得出、指得准、答不了敢拒 | 问一句中文，出可核对的 SQL 与结果 | 按规则清单查风险，给位置与证据 |
| 考的能力 | **能不能承认不知道** | **对错能不能被机器判定** | **主观判断怎么被工程约束** |
| 判定方式 | LLM judge + 人工锚点 | **EX 全自动，零 judge** | 确定性 21 条 + LLM 6 条（证据约束） |
| 数据 | 12 份合成制度 / 315 chunk | 6 表 / 8,584 行 / 10 类埋点 | 30 份合成合同 / 810 判定单元 |
| 评测集 | 主集 208 + 拒答 50 + 子集 80 | 主集 150 + 歧义 15 + 锚点 20 | 810 单元 + 报告质量 30 + 锚点 20 |
| 定稿指标 | 正确率 **68.00%**（facts，10-21 重跑；基线 50.65%）、Faithfulness 79.75%（基线）、judge 失败 **3.85%** → **INCOMPLETE** | EX **84.67%**、可执行 100%、JOIN 桶 68% | 存在型 100/100/100、缺失型 100%、语义召回 90.32% / 精确率 **100%** |
| 主要缺口 | 正确率、TTFT p95 4.0s | EX 差 0.33pp、JOIN 桶 68%、延迟 p95 5.2s | 门禁已全 PASS（v1.2）；仍缺长文分块、judge 自检集 |
| 功能 QA | 10/10 | 10/10 | 10/10 |
| 安全 | 路径穿越/空输入拦截、引用校验 | **四道闸 + 意图闸，对抗 12/12** | 上传限制、注入清洗、证据定位 |

## 二、这一次最值得写进课程的一句结论

**三次最大的指标提升，修的都是"尺子"，不是模型：**

| 项目 | 动作 | 收益 | 改的是 |
|---|---|---|---|
| ① | 口径从"整条条款"改"最小事实点" | 正确率 **+10.65pp** | 评测口径 |
| ① | prompt 加"逐子问题/禁推断时效" | Faithfulness **+17.4pp** | 生成层（唯一一次真改模型侧） |
| ② | 修 5 处评测器失真（展示截断、容差、gold 维度列、同名聚合、SLA 口径） | EX **+4pp** | **评测器与 gold** |
| ③ | 修一处标题匹配范围 | 缺失型 **+23.3pp**（76.67→100） | 检测逻辑一行 |

**推论（可直接进教材）：** AI 应用的"指标不达标"至少有四类原因——**尺子、题库、闸门、模型**。前两类占的比重，通常远超团队直觉。

## 三、八环在 AI 应用上的改编（逐环）

| 环 | GStack 原意 | AI 应用必须补的东西 | 三案例的实证 |
|---|---|---|---|
| **0 数据与口径** | GStack 无此环 | 指标可判定句、样本量、题料同源陷阱、**判定单元** | ② 按"合同/规则"计 30 份 ±14pp，改 810 单元才可测；③ 同理 |
| 1 需求 | office-hours 逼问 | 可压缩，但"不做清单"必须写 | ① 7 条不做；② 5 条；③ 6 条 |
| 2 SPEC | 规格与验收 | 每条 AC 加**测量方式 + 分母 + 证据文件** | ① 10 AC；② 10 AC；③ 14 AC |
| 3 会审 | 多角色挑刺 | **必须加"数据合规"与"领域立场"两个声音** | ② 未做 → codex 5 条"会审本该问"的漏洞；③ 未做法务 → 规则无立场 → **20/27 语义误报** |
| 4 施工 | 按规格编码 | **先做"可判定性"**：主键/外键能否支撑对账 | ② 账单不挂 `order_id` → 应收不可校验（误报 127 行） |
| 5 题库 | 无此环 | 题库是工程，要有**不变量断言** | ② 有 LIMIT 必须有序、题面覆盖每列；③ 每条规则至少被违反一次（拦下 9 条无区分度规则） |
| 6 QA | 实机探索 | **评测工具本身要自检** | ① judge 42% 失败；③ 语义 JSON 截断致召回假低至 16% |
| 7 发布 | 发版门禁 | 发布 ≠ 达标，Known issues 必须单列 | 三项目都是"功能全绿 + 指标未达标"发布 |
| 8 复盘 | 量化回看 | 把坏数字拆成**测量 / 能力 / 环境**三类 | ③ 47.62% 定位率=分母问题；①② 延迟=环境问题 |

**GStack 只有两个硬数字门禁**（spec ≥7/10、ship 覆盖率 60%/80%）——对 AI 应用不够用。三案例的补充门禁共识：

```
数据完整性断言全 PASS → 尺子自检通过 → 主集评测跑完 → 未达标如实 FAIL → 才允许发布
```

## 四、FDE 场景最佳实践（12 条，全部有出处）

### 4.1 口径与验收（最容易被客户问倒的部分）

| # | 实践 | 出处与证据 |
|---|---|---|
| **BP-1** | **口径先行 + 双口径双报**：指标必须写成"测量对象+口径+分母+方法+阈值"，口径一改必须两列并报、禁止跨口径比较 | ① 口径变更带来 +10.65pp；② +4pp；③ 定位率拆分 |
| **BP-2** | **判定单元 = 规则×样本**，不按文件计 | ③ 30 份合同 ±14pp，810 单元才可测 |
| **BP-3** | **题料同源要主动声明**：从语料反推生成的问题，召回避然虚高 | ① Recall@5 100%，异源冒烟仅 91.67% |

### 4.2 闸门与安全

| # | 实践 | 出处 |
|---|---|---|
| **BP-4** | **双闸分级**：硬闸（必须拒）+ 软闸（提示后继续）；写操作显式拒绝，不静默改写 | ② 意图闸：4 条业务问句被误拒后收紧；advisory 率 17.33% |
| **BP-5** | **授权器优于黑名单**：默认拒绝 + 白名单 | ② authorizer 原黑名单兜底，被 codex 抓出可绕过；改后对抗 12/12 |
| **BP-6** | **LLM 不得新增规则**，只能对给定 id 作答 | ③ `semantic.py` 白名单约束 |
| **BP-7** | **判违规必须有原文证据**，且证据要能定位、要属该规则主题；**并显式声明审查立场** | ③ 主题守卫把精确率从 18.75% 拉回 51.79%，再加立场字段到 **100%** |

### 4.3 测量可信度

| # | 实践 | 出处 |
|---|---|---|
| **BP-8** | **尺子必须先被量**：judge 自检集 10 条 + 比对器单测 5 例，跑评测前先跑它们 | ① judge 42% 静默失败；② 比对器 5 处失真；③ 因缺 judge 自检集，语义层翻车 |
| **BP-9** | **一次输入量有上限**：长材料分片 + 多模型回退 + **对空响应显式断言** | ② 3–6 万字符送审返回"200 + 空内容"；③ 语义 JSON 截断致召回 16% |
| **BP-10** | **先诊断再设计**：逐条打印失败样本（10 分钟）优于按直觉做结构性改造（半天） | ③ 7/7 FN 源于一处匹配范围，原方案是"模板域先验" |
| **BP-11** | **换分母不算提升**：口径调整必须标注，旧口径只作对照 | ③ 定位率 47.62%→100%，真实含义是"分母剔除无位置项" |

### 4.4 记录与交付

| # | 实践 | 出处 |
|---|---|---|
| **BP-12** | **"没做"也要记录**：裁剪要写原因与代价；证据要有索引；入口文档必须有 | ② 环 3 会审被跳过且未记录（`docs/07` 审计）；①② 42/43 份证据无索引 |

## 五、FDE 现场建议（对客视角）

### 5.1 怎么谈验收

| 客户原话 | 不要直接答应 | 建议改写成 |
|---|---|---|
| "准确率 ≥85%" | 一个数字 | "在 N 条人工标注题上，按 X 口径判定的正确率 ≥85%，判定方式为 EX/judge+抽检，N≥200" |
| "响应 ≤3 秒" | 端到端承诺 | "TTFT p95 ≤1s / 完成 p95 ≤4s"；并说明这是**环境依赖指标**（共享网关实测抖动 1.5s–18s） |
| "数据不出域" | 同意 | "嵌入/生成经本地网关，上游为云端模型；如需物理隔离需专用部署" |
| "幻觉 ≤10%" | 一个比例 | "Faithfulness（无依据断言比例）≤10%，由 judge 判定 + 人工抽检 20%" |

### 5.2 交付物清单（三案例共同沉淀）

```
必交：README（入口）/ SPEC / DECISIONS（含 Rejected）/ ENVIRONMENT / BUILD
     / qa-report（含失败样本）/ review（独立评审 + 处置）/ retro
     / 操作手册（可照着验）/ evidence 索引（每个数字的出处）
选交：八环讲解记录（内训/复盘用）/ 演示脚本（含失败演示）
禁止：只有截图没有证据链的"验收报告"
```

### 5.3 时间分配（三案例实测外推）

| 阶段 | 占比 | 说明 |
|---|---|---|
| 口径 + 数据 | **30%** | 三项目都在这步花了最多时间，也是收益最大的一步 |
| 施工 | 25% | 代码量最小的一部分 |
| 题库 + 评测 | **30%** | ② 的题库改动直接决定 4pp；③ 的题库内部矛盾导致 recall 50%→100% |
| 评审 + 复盘 | 15% | codex 抓出的问题改变过两个项目的结论 |

### 5.4 演示原则

- **主动演示失败**：拒答、写操作被拒、`not_detected`、PDF 不支持——比演示成功更有说服力。
- **数字带口径与限定词**：说"合成语料上 100%"，不说"准确率 100%"。
- **失败时不掩饰**：③ 演示脚本明确写了"报出明显误报时主动指出是立场未定义"。

## 六、反模式清单（每个都真踩过）

| 反模式 | 后果 |
|---|---|
| 用展示层数据做评测 | ② 压低 EX 4pp |
| 让被测模型自判对错、且不自检 | ① judge 42% 静默失败 |
| 用整篇文档当标准答案 | ① 正确也被判半对 |
| 只写文字规则、不给示例 | ② JOIN 规则写了但模型不遵守（桶 68%） |
| 一次性大 prompt 求稳 | ② 长输入空响应；③ 语义 JSON 截断 |
| 数据生成器的默认分支随手写 | ③ 每份合同自带缺陷 → 语义精确率 18.75% |
| 砍掉会审 | ② 5 条契约漏洞晚发现；③ 20 个立场误报 |
| 口径只报新版 | 数字好看但不可比 |

## 八、一句话总结

**三案例证明的不是"我们能做 AI 应用"，而是：**

> 在 FDE 场景里，一个 AI 应用能不能交付，取决于**三件与模型无关的事**——口径能不能定死、判定能不能自动、证据能不能追溯。
> GStack 八环提供了纪律骨架，但必须补三样东西：**环 0（数据与口径）、题库工程、测量自检**。
> ①② 的指标仍未全达标（50.65% / 83.33%，10-20 基线 84.67%），③ 在 v1.2 门禁全 PASS 但仍有未修项；而**每一次提升都来自修尺子、修题库、修一处逻辑（含一处立场字段），不是换模型。**
