# AI 应用八环改编指南与跨案例复用清单

> **定位说明（用户 2026-10-20 明确）：**
> - **R1–R3.5（FruitLab）是工具层教学**：在确定性 CRUD 应用上把 GStack 八环、门禁、产物契约讲清楚。
> - **本目录三个案例是方法层"举一反三"**：用 RAG / NL2SQL / 合同审查三个更具代表性的 AI 场景，把课程从"会用工具"提升到"能广泛复制的方法"。
> **因此本文的判据是：** 一条经验只有能**脱离 RAG 被复制**，才算本轮的真产出；只对 RAG 有效的不写进来。

## 一、方法层沉淀：7 条可复制的做法

每条都给出"本轮证据 → 迁移到 ② NL2SQL → 迁移到 ③ 合同审查"。

### M1 环 0「数据与口径」是 AI 应用的第一性工序

**本轮证据：** 客户给的 6 组指标全部缺口径。环 0 把"召回≥90%"改写成"gold chunk 被 top-5 命中的比例"，并算出 5pp 判定需要 n≥200。这个动作让后面所有评测有了共同语言。

**方法内核（与业务无关）：** AI 项目的验收指标必须写成

```
指标名 = 测量对象 + 口径 + 分母 + 测量方法 + 阈值 + 置信条件
```

**迁移到 NL2SQL：**
- "解析准确≥85%"→ 定为 **EX（执行结果一致率）**，含比对规则（列顺序无关、浮点容差、空值语义）。
- 分母 = 题数；≤3 表如何界定（JOIN 深度还是涉及表数）；**多轮先明确排除**。
- 延迟拆成"首次返回（含 SQL）"与"结果完成"，与 RAG 同构。

**迁移到 ③ 合同审查：**
- **分母是关键决策**：从"合同"改成"规则×合同判定单元"——20 份合同时 CI ±14pp（等于没测），27 规则×30 份=810 单元时 ±2.2pp，采集成本一样。
- **存在型与缺失型必须分开报**（缺失检查是通用模型的系统性弱项）。
- 召回必须**成对考精度**，否则等于奖励乱报。

---

### M2 双闸原则：能确定性判的，绝不交给模型

**本轮证据：** 只靠 prompt 时，"字面相似但语义无关"的 chunk 会诱导模型硬答；加了 rerank 分数阈值（0.30）后，无答案问题的 top1 只有 0.0003，直接拒答且**不调用模型**（658ms）。

**方法内核：** 每条安全/正确性要求都配一道**确定性闸**（阈值、白名单、正则、存在性检查），模型只负责"语义部分"。

**迁移到 NL2SQL（这道闸更硬）：**
| 闸 | 确定性实现 |
|---|---|
| 只读 | 数据库账号物理上没有 DDL/DML 权限 |
| 表/列白名单 | AST 解析后比对登记表，越界即拒 |
| 多语句注入 | 禁 `;` 多语句、禁注释绕过 |
| 结果集上限 | 强制 LIMIT，默认 1000 行 |
| 纠错次数 | ≤2 次，每次重新过白名单 |

**迁移到 ③ 合同审查：**
- 数值类（比例、期限、金额门槛）**交代码算**，不交模型（业界"双引擎"做法）。
- 缺失项**不走纯 LLM**：先建"应有条款域清单"，再用关键词+编号+语义三重存在性检查。
- 本轮 RAG 的"废止/时效探针"就是同一模式：**确定性补充检索**，零额外 API 成本。

### M3 四类契约先行：输入 / 中间产物 / 输出 / 可追溯

**本轮证据：** SPEC 定死 chunk 记录、索引元信息、SSE 事件序列、trace 字段。后续所有争议都能落到某个字段上。

**方法内核：** AI 应用必须有四份契约，缺一份就会出现"跑得通但说不清"。

| 契约 | RAG | ② NL2SQL | ③ 合同 |
|---|---|---|---|
| 输入 | doc_id/page/clause 元数据 | 问题 + **语义层版本** | 文档 + **规则清单版本** |
| 中间产物 | 检索候选与分数 | 候选 SQL + 校验结果 + 重试次数 | 条款切分 + 规则命中 + 置信度 |
| 输出 | 答案 + 引用编号 + 拒答标记 | SQL + 结果集 + 图表规格 | 风险卡片 + 等级 + 依据条款 |
| 可追溯 | trace（含改写 query） | trace（含 schema 裁剪快照） | trace（含规则版本与模型版本） |

**共同要求：输出里的每个引用/结论，都必须能被服务端校验，而不是信任模型。**

### M4 分层评测 + 双口径 + INCOMPLETE 门禁

**本轮证据：** 全量 208 条带 judge 需 60 分钟以上；改"全量无 judge（15 分钟）+ 80 条分层子集带 judge（12 分钟）"。新增口径后强制双报，并规定"judge 失败率 >2% 判 INCOMPLETE"。

**方法内核：**
1. **两层跑**：便宜指标全量跑，贵指标分层子集跑（子集必须含全部难例分桶）。
2. **双口径并列**：口径一改，数字不可比；报告必须两列 + 明确声明。
3. **测量可信度门禁**：judge 失败率、抽样比例、人工一致率进报告；不可信则 INCOMPLETE，**禁止输出 PASS**。

**迁移到 NL2SQL（最大优势）：** EX 完全可自动计算，**不需要 LLM judge** → 天然绕开本轮最大坑（judge 不稳定）。建议 100% 自动判定 + 人工锚点 20 条校准。
**迁移到 ③ 合同：** 必须用 judge 或人工 → 直接继承本轮三条硬规则：judge `max_tokens` 要够（≥2500）、字段结构化、失败率超阈值判 INCOMPLETE。

---

### M5 独立智能体评审：抓"数据坏了但链路活着"

**本轮证据：** codex 评审出 26 条，Critical 那条是 `# 标题` 吞掉元数据 → 327 个 chunk 的 `status/effective_date` 全空、标题块被选进出题池。**而自测指标是"召回 91.7%、引用 100%"。**

**方法内核：** 自测只能证明"链路通"，不能证明"数据对"。必须有一个**不同进程、不同上下文**的评审方，拿着一份"该查什么"的清单去查。

**迁移到 ② NL2SQL 的高发同类问题：**
- schema 链接错（选对表但选错列）→ 链路通、结果错
- 结果集比对口径错（列顺序/精度/空值）→ 指标虚高
- 语义层版本与库不一致 → 线上口径漂移

**迁移到 ③ 合同的高发同类问题：**
- 条款切分错位（跨页、表格）→ 引用指错
- 规则清单与评测集同源 → 指标虚高
- 风险等级定义在规则里与报告里不一致

**可复制的评审 prompt 骨架**（本轮 `evidence/review-prompt.txt`）：只报真问题、每条给文件:行号+触发条件+修法+严重度、指定"必须检查的清单"、要求 Top3 最高风险、禁止改文件。

---

### M6 变量隔离攻坚：A 直接修 → B 轻量 spec → C 环境 A/B

**本轮证据：** A 段（prompt）Faithfulness +17.4pp；B 段（口径）正确率 +10.65pp；两件事分开做才分得清归因。若同时改，17.4 与 10.65 就永远说不清是谁的功劳。

**方法内核与顺序不可换：**
1. **A**：改生成层（单点、可回滚、同口径可测）
2. **B**：改尺子（触及验收标准 → 走轻量 spec + 会审 + 人拍板 + 双报）
3. **C**：环境/模型 A/B（只记证据，不动主线）

**迁移到另两个案例：** 完全同构。NL2SQL 的 A 段是 prompt 与 few-shot；B 段是 EX 口径与"解析正确"定义；C 段是模型与语义层方案对比。合同同理。

---

### M7 人类锚点集：每个 AI 项目至少 20 条

**本轮证据：** 20 条人工无偏题 + 8 条人工判定，直接暴露了两件事：Recall 100% 是题料同源；h-04 是真错（只答 30 分钟漏 15 分钟）。

**方法内核：** 自动指标会自欺，必须有一小份**人类亲手写、且与语料不同源**的锚点数据，用来校准自动指标。

**迁移到 ② NL2SQL：** 20 条人工题（含歧义、脏数据、需澄清的题），核对自动 EX 与人工判断是否一致。
**迁移到 ③ 合同：** 10–20 份人工标注样本（规则×合同判定单元），同时作为客户抽检 20% 的基础。

## 二、反向规则：本轮踩过、下一轮不要再踩

| # | 不要做 | 本轮证据 | 下一轮改为 |
|---|---|---|---|
| N1 | 不要用"链路全绿"当验收 | 召回 100% 时元数据全空 | 先跑数据完整性断言（元数据非空、条款号非空、gold 指向正文） |
| N2 | 不要为省 token 压 judge 的 `max_tokens` | 800 被思维链吃光，42% 判定失败 | judge ≥2500，或改用无思维链模型做结构化输出 |
| N3 | 不要并发跑评测与其他任务 | 网关争抢，19 秒/条，35 分钟只跑 20 题 | 评测前先做 10 条吞吐标定；跑批独占网关、串行执行 |
| N4 | 不要在测试集太小时做选型对比 | 12 份语料 → 三款嵌入都是 100%，无区分度 | 先把数据规模做到能区分（段落级/条款级、≥30 份、表 ≥3 张千行） |
| N5 | 不要把"拒答"当单一布尔值 | 答案开头含"资料不足"被误标 `refused`（R-29） | 分三态：`answered` / `insufficient_disclosed` / `refused` |
| N6 | 不要让评测集与语料同源 | 单跳/多跳题从条款反推，Recall 必然 100% | 锚点集必须**人工独立出题**、与出题流程隔离 |

## 三、三案例差异化设计（避免三个 demo 长得一样）

这是"举一反三"最容易做砸的地方——三套 demo 都变成"接个大模型、做个问答页"。建议按**考什么能力**分工：

| 案例 | 考的能力（一句话） | 教学锚点 | 验收侧重 |
|---|---|---|---|
| ① RAG | **能不能承认不知道** | 证据边界与拒答 | 拒答率、冲突并列、引用可定位 |
| ② NL2SQL | **能不能守住边界** | 确定性安全边界 + 可自动验收 | EX、只读/白名单、LIMIT、零 judge |
| ③ 合同 | **能不能分级与复核** | 规则可维护 + 人机协同 | 存在型/缺失型分报、精度成对、复核闭环 |

三者的方法层共性正好构成一条主线：**从"答对"（①）→ "算对且不出界"（②）→ "判得准且能追溯责任"（③）**。这条递进关系可以作为课程的主叙事。

## 五、下一轮 SOP（以 ② NL2SQL 为例，可平移到 ③）

| 步 | 动作 | 产出 | 门禁 |
|---|---|---|---|
| 1 | 环境与能力探测 | `ENVIRONMENT.md` | 三项能力（生成/嵌入/重排）实测通过 |
| 2 | 环 0 口径 | `docs/00-数据与口径.md` | EX 定义写成可判定句；n≥150；judge 自检集通过（若用 judge） |
| 3 | 数据与语义层 | 建库脚本 + 语义层 | 表 ≥3、行 ≥千、含脏数据；语义层版本入库 |
| 4 | SPEC | `SPEC.md` | 每条 AC 可测；四类契约齐 |
| 5 | 施工 | 检索/生成/校验/图表 | 只读闸、白名单、LIMIT 三条硬校验先落地 |
| 6 | 自动评测 | `EVAL-REPORT.md` | **零 judge 依赖**；全量跑 |
| 7 | 锚点校准 | 20 条人工核对 | 自动 EX 与人工判断一致率 ≥85% |
| 8 | 独立评审 | `review.md` | 清单含 schema 链接/结果比对/版本漂移 |
| 9 | QA + 发布 + 复盘 | 同本轮 | 未达标如实记 Known issues |

**时间盒建议（按本轮实测外推）：** 环境+口径半天、数据+语义层 1 天、施工 1 天、评测与迭代 1 天、评审 QA 复盘半天，合计约 4 天。**评测要占 1/3**——这与 CRUD 项目最大的不同。

## 六、方法层仍空白、需要下一轮补的

1. **评测工具自检规范**：judge 自检集、吞吐标定、抽样比例、人工一致率——本轮是踩坑后才补的，应写成环 0 的标准动作。
2. **"数据不出域"的可复制结论**：当前三个案例都会依赖云端 provider，只有 RAG 明确记录了边界。建议在②③开工时统一写一份"部署形态与合规边界"模板。
3. **多轮问答的评测方法**：本轮把多轮排除在验收外，属回避。若课程要讲"会话式 AI"，需要一套多轮评测设计（指代改写准确率、上下文截断影响）。
4. **成本指标**：本轮只零散记了 token，没有单次成本/月度预算的口径。三个案例都该加这一行——客户一定会问。
5. **失败演示脚本的标准化**：本轮写了 `docs/06-演示脚本.md`，但"主动演示失败"的四类负例应抽象成通用模板（无答案/越权/冲突/需审批写操作），直接套到②③。

## 七、一句话

**本轮真正的产出不是"RAG demo 跑通"，而是证明了五个可脱离场景复制的方法：口径先行、双闸原则、四类契约、分层评测+双口径、变量隔离攻坚。** ②③ 应当**先复用这五条，再补各自特有的领域能力**（②的语义层与 SQL 校验、③的规则 DSL 与缺失检测），而不是从零再摸索一遍。
